本文件按五个业务模块整理“模块名字、模块功能及对应接口和数据库表、架构目录”，补充公共登录入口。功能以需求和接口方案为依据；表名优先对照当前 `scripts/sql/all.sql`；接口是否已有代码、是否挂载分别说明。未连接数据库、未启动服务，因此“已有代码”不代表已经部署或通过联调。

接口表中的数据表为主要业务表及共享依赖，查询表示读取，提交/修改表示按业务写入；方案阶段的表映射按设计归纳，不表示已经执行。目录只列实际文件夹，省略 `.git`、`__pycache__`；当前后端按技术层共用目录，未划分五套模块专属代码文件夹。

通用操作：先登录取得 Token，再在受保护请求中带上 `Authorization: Bearer <access_token>`。多数接口采用 `{code,message,data}` 响应，`code=0` 表示成功；S01 请假当前代码还使用实际 HTTP 错误状态，调用方应同时检查 HTTP 状态和业务码。企业方案写操作使用 `Idempotency-Key`，修改操作另传 `expected_version`；学生请假提交必须带幂等请求头，报告配置修改使用 `row_version`。各接口具体请求字段以对应接口方案或代码为准。

## 一、客户研判

**模块名字：** 客户研判。

**模块功能以及对应的接口和对应的数据库表：**

录入客户文本或上传文件，抽取客户信息，按产品画像规则生成匹配结论、等级、原因与证据，支持历史记录查询。操作顺序为“录入/上传 → 提交研判 → 查看各产品结论 → 查询历史详情”。方案允许 Dify 增强，并保留本地规则处理。

**当前状态：** 当前系统目录未发现客户研判 API、模型和服务实现，以下四个接口按方案列出。`customer_info`、`customer_judgement`、`judgement_rule` 出现在设计文档中，但不在当前统一建表脚本中；须补齐实现和建表后才能联调。客户研判结果表与企业客户档案 `customer_profile` 不是同一张表。

| 编号  | 模块功能 / 操作     | 对应接口                                        | 对应数据库表 / 数据来源                                                        |
| --- | ------------- | ------------------------------------------- | -------------------------------------------------------------------- |
| J01 | 提交文本或文件并生成研判  | `POST /api/v1/customer/judge`               | `customer_info`（写）、`judgement_rule`（读）、`customer_judgement`（写）；均为设计表 |
| J02 | 查询单条研判结果及解析字段 | `GET /api/v1/customer/judge/{judgement_id}` | `customer_judgement`、`customer_info`（读，设计表）                          |
| J03 | 查看产品画像规则      | `GET /api/v1/customer/rules`                | `judgement_rule`（读，设计表）                                              |
| J04 | 查询历史研判记录      | `GET /api/v1/customer/records`              | `customer_info`、`customer_judgement`（读，设计表）                          |

## 二、客服 Agent

## 三、企业智能助手（企业管理）

**模块名字：** 企业智能助手，接口方案中称为“企业管理模块”。

**模块功能以及对应的接口和对应的数据库表：**

覆盖客户档案与跟进、日报、组织通讯录、学生档案与成绩、请假审批、投诉处理、心理预警处置、知识问答、待办通知及自然语言办理。常用操作包括“录入客户 → 跟进 → 更新状态”“整理日报预览 → 正式提交 → 修订/查阅”“接收学生待办 → 审批或处理 → 留痕并通知”。AI 修改业务先返回确认预览，再调用固定业务服务执行，NL2SQL 只用于查询。

**当前状态：** 企业接口方案为评审设计，列出 60 个业务/协作接口和 19 个管理配套接口，不能视为 79 个已实现接口。当前 `main.py` 引用了不存在的 `app.api.enterprise_student`，完整应用启动存在缺失模块问题。企业方案的员工、客户、学生、工单、知识及审计相关表已列入统一 DDL；未核验实际数据库。

权限按 `employee/consultant/manager/teacher/academic/admin` 六类角色及有效数据关系控制。顾问限本人客户，主管限授权部门，老师审批限分派和学生关系，教务成绩限学生及课程范围；心理预警另需专属授权。管理员配置权限不自动获得全部业务数据权限。

以下表格列出完整接口路径。各组表映射中的员工、学生关系用于数据范围校验；企业写操作通常还涉及 `operation_log`，通知按事件写入约定的通知表。

### 059. 学业提醒设置代次、精度与对象版本映射

### 060. 外部同步等时冲突、迟到变更与来源优先级

**解决规则：** 本地维护使用可信本地ID、source_system=local，source_updated_at是单调推进的本地权威变更时间，synced_at留空，不伪造外部同步。外部未来以“学生、来源系统、外部节点/申请ID”为唯一来源键，不按姓名或标题猜映射。

| 到达事件         | 处理                                  |
| ------------ | ----------------------------------- |
| 源时间更新且有写权    | 接受，按真实变化推进业务/提醒版本，成功更新synced_at     |
| 等时同规范化业务内容   | 幂等成功，不推进业务版本、不重复提醒，可记录成功确认synced_at |
| 等时异内容        | 记录受控冲突、拒绝覆盖、不刷新synced_at            |
| 更旧，包括迟到改期/删除 | 记录忽略，不覆盖、不刷新synced_at               |
| 来源不符或映射缺失    | 拒绝并进入映射/冲突处理，不覆盖其他来源                |

比较包含受控业务字段及有效/删除状态，排除接收次数和synced_at等元数据，源时间统一UTC六位精度，缺失则拒绝。同时间戳不足以排序时提供可信源版本或进入冲突处理，不用接收时间替代。

来源唯一归属：本地阶段仅local写；外部启用需显式切换，节点交获准教务来源、申请阶段交获准CRM来源，普通同步不能变更归属。本地紧急更正需专门权限、原因、原值和人工保护标记，解除保护前外部变更进冲突队列，不静默覆盖。映射、保护、冲突记录须持久化。

删除保存为带源版本的取消/失效事件和墓碑，不物理删除有引用对象，防旧消息复活；节点取消推进版本、废止提醒。申请阶段删除先有明确失效状态映射，否则拒绝，不自造状态；快照缺行不自动当删除。

可信源事件ID或来源唯一键+源时间+规范化内容摘要作稳定幂等键。同事务完成去重、版本比较、事实更新、提醒重排和通知入队，失败整体回滚，不刷新synced_at；学业锁序同059。批量按来源键排序、每条独立事务返回结果，成功项重放不再执行，拉取批次未完整成功不推进游标。临时故障按1、5、15、60、240分钟重试后进人工失败清单；参数、映射及等时冲突不自动重试，每次重试重新比较权威版本。

**待实施与验收：** 本地按原契约建设，外部适配待结构就绪后启用；覆盖等时幂等/冲突、迟到删除不覆盖改期、墓碑防复活、不同来源同名不误并、人工保护有效及失败不刷新同步时间。
