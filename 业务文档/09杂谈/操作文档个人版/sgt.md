本模块接收来自文本、PDF 简历、Excel 表格等多种形式的客户信息，解析并结构化提取关键字段，依据甲方提供的《用户画像研判规则》自动判断客户是否符合甲方公司两个产品的目标客户画像，并输出结构化研判结论。以下说明区分「依据需求的设计能力」与「建议补充项」；本文档为个人操作说明，实现细节以代码为准。

## 一、模块功能以及对应的接口和对应的数据库表

本模块对外提供客户信息接入、解析结构化、画像研判、结果查询等 HTTP 接口，并提供供各接口复用的多格式文件解析、研判规则引擎、日志、统一返回、异常处理及本地 Dify HTTP 请求等公共能力。研判结论严格依据《用户画像研判规则》得出，不依赖前端自报字段。

## 二、用户角色和接口鉴权

### 1. JWT 身份认证与逐接口鉴权

身份认证统一采用 JWT。权限校验由每个受保护接口调用公共鉴权中间件，依据用户表中的身份及对应权限，判断是否允许执行该接口。具体流程为：

1. 用户提交账号密码，后端查询用户表并验证密码哈希。
2. 登录成功后签发带有效期的 JWT，后续请求携带 `Authorization: Bearer <access_token>`。
3. 每个受保护接口先调用鉴权中间件，复用公共认证依赖校验 JWT 签名及有效期，通过 Token 的 sub 取得 user_id，再查询用户表取得真实身份。JWT 用于确认身份，接口权限以服务端当前用户记录和权限配置为准。
4. 用户表身份映射到 `app/access_control.yaml` 的权限集合。
5. 每个接口通过 `Depends(require_permission(...))` 声明所需权限，中间件检查通过后才执行接口；无有效 JWT 按 401 未认证处理，已认证但无权限按 403 禁止访问处理，响应信封及 HTTP 状态按第四节约定处理。
6. 业务服务继续校验具体记录的数据归属和业务状态，限制可操作的具体记录。

**当前设计说明：** 用户表保存身份，权限由权限配置确定；是否采用「身份→权限」还是「账号单独分配权限」需按项目既有约定实现，若为后者需增加权限关系表和查询逻辑，不能描述成已经支持。

权限由服务端用户记录和配置决定，不接受前端自报身份。前端隐藏菜单仅用于展示；直接请求业务 API 时仍须鉴权。

各接口分别声明所需权限，不复用「登录成功即可访问所有业务」的规则。登录和公开清单等明确公开的接口无需挂载受保护接口的权限依赖。业务需要新增权限时，由负责人提供权限标识、允许角色和数据范围，公共模块统一维护权限映射；业务负责人将鉴权依赖接入每个对应接口。

关联表：本模块直接使用 `customer_source`、`customer_info`、`research_rule`、`product`、`research_result`；其中 `customer_source` 通过 `customer_info` 关联结构化字段，`research_result` 关联 `customer_info` 与 `product`，规则的维护归本模块。

## 三、日志生成

各接口和研判服务获取公共日志工具，按需记录客户信息接入、解析结果、研判执行、规则版本、外部调用失败和异常信息。

日志默认输出到控制台和 `app/logs/` 下的日期命名日志文件，路径及等级由 `LOG_DIR`、`LOG_LEVEL` 配置。格式包含时间、级别、模块名称、行号和消息。

公共模块提供日志工具，各业务负责调用工具记录具体业务事件。文本运行日志与数据库中的业务审计不同；账号密码、Token、Dify API Key 不写入日志，客户敏感信息（联系方式等）按需脱敏。

## 四、统一返回格式及异常处理

各 HTTP 接口通过统一返回工具组织响应，固定包含 `code`、`message`、`data` 三个字段。

`code` 为业务状态码，`message` 为说明，`data` 为结果数据；成功为 0，常用失败码包括 400 参数错误、401 未登录、403 无权限、404 不存在、409 冲突、500 内部错误。

应用入口注册全局异常处理后，业务异常被转换为统一信封；未处理异常记录日志并返回通用内部错误。业务异常及未处理异常、HTTPException、参数校验异常的统一信封处理范围需与项目既有约定保持一致；若当前只有部分路径统一，需进一步统一异常出口和协议约定。

研判结果中的「是否命中」结论通过 `success()` 返回，命中/未命中均为正常业务结果，不使用异常表达业务判定失败；只有解析失败、规则缺失、文件无法读取等异常才进入错误分支。

## 五、调用本地 Dify 大模型：公共 HTTP 请求能力

本模块的核心研判依据是《用户画像研判规则》，应优先使用确定性规则引擎保证「严格依据规则、准确率不低于 95%」。对于 PDF 简历、非结构化文本等需要理解语义才能提取关键字段的场景，可选用本地 Dify 大模型辅助解析，但规则判定不依赖大模型输出。

| 分工 | 公共模块负责 | 业务模块负责人负责 |
| --- | --- | --- |
| 地址与连接 | 接收 Dify API 基础地址，拼接请求路径 | 确认使用的本地 Dify 服务和应用类型 |
| 应用凭据 | 使用传入的应用 Key 设置 `Authorization: Bearer ...` | 为解析应用配置独立 Key，交由服务端配置读取 |
| HTTP 请求 | 同步/异步 JSON POST、超时、HTTP 错误检查、JSON 对象解析 | 选择 `/workflows/run` 或 `/chat-messages`，组装对应请求体 |
| 模型能力 | 提供 HTTP 传输工具 | 模型、Prompt、知识库及字段抽取策略 |
| 返回结果 | 返回 Dify 原始 JSON 对象，底层异常交调用方处理 | 检查业务状态，提取关键字段、校验结构并转换为结构化结果 |
| 后续动作 | 不承担研判判定和数据写入 | 调用业务服务执行规则判定、落库和结果输出 |

### 调用方式

本地 Dify 基础地址默认从 `DIFY_API_BASE` 读取。各应用使用各自的 API Key；调用地址为后端可访问的 Dify 地址，模型供应商配置由各业务在 Dify 中维护。

同步业务调用同步 HTTP 方法，异步业务调用异步 HTTP 方法。应用 Key 从后端配置读取，不由浏览器提交，也不写入文档。调用用户标识由可信认证上下文生成。

当前工具只封装 JSON POST；SSE 流式输出、文件上传、自动重试、连接池长期复用、熔断和 HTTP 失败到业务错误码的统一映射尚未提供，各业务如需要应明确需求后扩展。工作流返回 HTTP 200 仍可能执行失败，必须由业务适配器检查，不能只依据 HTTP 成功判断模型调用成功。

各 Python 包内的 `__init__.py` 为包初始化文件，目录树省略重复列举。`clients/` 中的业务适配器用于说明公共 HTTP 工具的调用位置，不表示其模型配置和业务解析也由本模块负责人承担。数据库建表脚本由团队统一维护，客户研判相关模型与其保持一致。

各业务接入时，先为接口声明 JWT 认证和权限依赖，再按需使用公共配置、数据库会话、参数校验和日志工具；文件解析和规则判定调用本模块核心服务，结果通过统一返回工具输出。

## 附：关键数据字段与研判口径（依据需求整理）

- **客户信息来源**：`customer_source`，字段建议含 `source_type`（text/pdf/excel）、`raw_content`、`file_path`、`status`、`created_at`。
- **客户关键字段**：`customer_info`，建议含姓名、性别、年龄、学历、专业、工作年限、行业、职位、所在城市、收入/薪资、意向产品、联系方式等，具体以《用户画像研判规则》所需的字段为准。
- **用户画像研判规则**：`research_rule`，按版本保存，支持更新；对应甲方公司的两个产品（`product`），每条规则说明命中/未命中条件。
- **研判结果**：`research_result`，输出「是否命中产品 A / 产品 B、依据字段、规则版本、研判时间」，供后续业务或人工复核使用。
