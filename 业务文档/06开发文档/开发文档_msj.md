## 1. 文档定位与当前状态

本文件将现有业务需求转为可分工、可联调、可验收的开发方案。覆盖客户研判、客服 Agent、企业智能助手、学生智能助手、智能报告五个模块及其共用能力。项目目录当前只有 README 和业务文档，未发现应用代码、部署配置或测试代码，因此下文均为**待实现方案**，不是已完成情况。

现有接口与表结构作为设计基线；本文件提出的补充接口、字段、状态与安全措施标为“建议补充”，需在开发前由业务方和技术负责人确认。甲方原始规则、公司资料和外部系统契约未出现在当前目录，相关功能不能仅凭现有文档完成真实数据验收。

### 1.1 角色与边界

| 角色 | 主要能力 | 数据边界 |
|---|---|---|
| 访客/潜在客户 | 客服咨询、课程和活动查询、报名 | 仅访问公开资料及本人报名信息 |
| 学生 | 请假、投诉、学业和申请进度查询、生活问答 | 仅访问本人数据 |
| 员工/班主任 | 客户跟进、日报、学生审批和工单处理 | 仅访问授权客户、班级或工单 |
| 管理员/管理层 | 规则和知识库维护、团队日报、统计报告 | 按部门和敏感级别授权 |
| 系统任务 | 提醒、报告生成、同步和预警推送 | 使用独立服务身份和最小权限 |

本期不建设 CRM、教务、支付、合同、人事薪酬或人工客服工单系统本体；涉及 CRM/教务的需求通过适配接口接入现有系统。学生投诉工单属于本项目售后流程。

## 2. 总体实现方案

建议采用“客户端/渠道 → API 服务 → 业务服务 → AI 能力及外部适配器 → 业务库/知识库”的分层结构。实际编程语言、数据库产品、模型供应商和部署平台在现有资料中未指定，选型时以可审计、可替换、可运维为准。

| 层 | 主要职责 | 交付物 |
|---|---|---|
| 接入层 | Web/移动端或已有渠道接入、登录、会话和上传 | 页面或渠道适配、统一鉴权 |
| API 层 | `/api/v1`、参数校验、权限检查、幂等、响应封装 | OpenAPI 契约、接口实现 |
| 业务层 | 研判、报名、客户、请假、工单、报告等确定性流程 | 服务、状态机、审计事件 |
| AI 能力层 | 意图分类、语音转写、信息抽取、RAG、摘要、受限 NL2SQL | 模型适配、提示词版本、评测集 |
| 数据及集成层 | 关系库、向量索引、文件存储、CRM/教务适配、消息和定时任务 | 迁移脚本、同步任务、监控 |

所有写操作须由业务服务按权限及状态机执行；模型只输出结构化意图和参数，不直接执行 SQL、审批或通知。知识问答需返回来源标识、文档版本和更新时间；检索无充分依据时提示转人工核实。留学政策类内容必须有维护责任人与生效/复核时间。

### 2.1 共用处理链

1. 接入请求并识别用户身份、角色、会话和租户/部门范围。
2. 对文本、语音或文件做格式校验、大小限制、恶意文件检查和必要脱敏。
3. 进行意图识别；低置信度或多意图时要求澄清，不能猜测写入对象。
4. 查询场景走 FAQ、结构化数据查询或 RAG；写入场景走参数确认、授权和业务服务。
5. 返回结果及必要的来源、状态、下一步；记录请求 ID、耗时、模型/规则版本和审计日志。

## 3. 模块开发设计

### 3.1 客户研判

**输入与处理：**支持纯文本、PDF 和 Excel；文件先上传至受控存储，解析器按类型抽取文字及表格，再规范化为客户字段。解析结果需保留来源位置与缺失字段，避免将模型推断当成事实。批量 Excel 按行生成独立研判任务和错误清单。

**规则执行：**《用户画像研判规则》按产品分别版本化，采用“字段校验 → 规则匹配 → 证据记录 → 结论”流程。为两个产品分别输出匹配状态、命中/未命中规则、原因和规则版本；关键字段缺失时输出“待人工复核”，不强行判为不匹配。规则更新后，新任务使用新版本，历史结果保留原版本以便追溯。

**交付与验收：**解析结果可人工校正；支持单条、批量研判和结果查询。以业务方标注样本集评估研判准确率，目标不低于原需求的 95%；同时单独统计解析失败、字段缺失和待复核比例。没有《用户画像研判规则》及两个产品定义前，只能完成框架和模拟规则联调。

### 3.2 客服 Agent

**七类场景：**公司信息、公司业务、留学政策、课程项目推荐、活动报名、FAQ、闲聊。先分类，再按场景调用结构化查询或知识检索；一个消息可识别多个意图，依次处理或请用户选择。

**知识库：**《公司信息》《公司业务》《留学政策》切片后写入向量索引，保存文档 ID、章节、版本、适用国家/地区、有效期和维护人。FAQ 走精确/语义匹配；课程、活动和报名以业务数据库为准。知识更新需经过导入、校验、发布、回滚流程，过期政策应停止作为确定性答案的依据。

**推荐与报名：**推荐前收集学历背景、意向国家等必要条件，使用课程适用人群规则筛选，再由模型生成解释。报名检查活动是否有效、容量及重复报名，创建报名记录并返回确认信息；失败时不声称报名成功。

**验收：**按七类场景的标注测试集计算意图识别准确率，目标 ≥90%；FAQ 回复目标 ≤1 秒（明确测量环境与分位数后执行）；知识问答准确率目标 ≥95%，并逐例核查是否有可追溯来源。原需求中的“无幻觉”应落实为无依据拒答、人工复核及错误答案统计，不能仅靠提示词承诺。

### 3.3 企业智能助手

**客户与日报：**文字/语音输入先转写、抽取并展示待确认字段，再写入意向客户或日报。客户状态使用明确枚举和合法流转；跟进记录追加保存，不能覆盖历史。日报保留原始转写和结构化摘要，允许本人修订；管理查询按部门授权。

**组织与新人指引：**组织架构需接入权威人事/通讯录数据源，展示部门职能和授权范围内联系方式。新人指南可先上线 QA，再导入制度文件做 RAG；制度答案应显示来源和版本。

**学生业务综管：**成绩录入与查询、请假审批、投诉跟进分别调用业务接口。自然语言指令解析为 `{action, target_id, parameters}`，目标重名、信息不全或高影响操作必须二次确认；审批、成绩更改和投诉结案记录操作人、时间及前后状态。

**NL2SQL：**仅开放授权的只读视图/字段白名单；只允许参数化 `SELECT`，限制结果行数、超时和扫描范围，禁止模型拼接原始 SQL 直接执行。对用户返回业务结果和查询条件，不默认暴露 SQL 或其他人的敏感字段。以标注问句集验收查询语义正确率，目标 ≥90%，并测试越权、注入和歧义场景。

**主动待办：**按班主任、员工和部门关系查找待审批请假、待跟进投诉等，消息去重并保留已读/处理状态；推送失败可重试，不能重复执行审批。

### 3.4 学生智能助手

**七类场景：**行政服务、心理关怀、售后反馈、学业考务、进度追踪、生活支持、增值转化。登录后的 `student_id` 从会话身份解析，不能信任客户端自行传入的任意学生 ID。

**请假闭环：**学生提交 → 创建待审批单 → 按归属推送班主任 → 班主任审批/驳回 → 更新状态 → 通知学生。审批接口须校验当前状态、审批人权限和重复请求；消息投递与业务状态分离，失败重试。

**投诉闭环：**提交投诉/建议 → 抽取摘要和类别 → 创建工单 → 分派跟进人 → 更新处理状态及方案 → 通知学生。记录首次响应与结案时间，供投诉周报计算处理时效。企业侧 `complaint_feedback` 与学生侧 `after_sales_ticket` 的主从关系须先确定，建议以同一工单为事实源，避免双表独立写入。

**学业与进度：**通过教务适配器读取 DDL、考试时间，通过 CRM/申请系统适配器读取文书、院校、签证状态。展示数据更新时间；外部系统不可用时返回“暂时无法更新”及最近一次有效数据时间，不能编造进度。提醒按用户时区、偏好和节点去重发送。

**生活与转化：**生活指南 RAG 输出地区和来源；紧急求助信息需定期核验。升学项目推荐以有效项目库和学生明确意向为前提，提供关闭推荐的入口，避免在心理风险或投诉场景插入营销。

**心理风险：**情绪识别用于辅助提醒，不能作为诊断。高风险输入生成预警并通知授权老师人工跟进；建立通知失败升级、处理记录和访问审计。对紧急风险先提供即时求助引导，再启动人工处置。心理原文、画像和报告设置更严格的访问与保留规则；周报优先使用去标识化聚合数据。

### 3.5 智能报告

| 报告 | 数据来源 | 必备输出 |
|---|---|---|
| 全域客户经营分析 | 意向客户、状态历史、跟进/成交/流失记录 | 新增、转化、流失、同环比、特征与归因；标明统计口径 |
| 员工日报（日/周） | 员工日报 | 核心进展、产出、风险、未提交情况 |
| 学生心理周报 | 情绪画像、预警及跟进 | 匿名化总体趋势、风险分布、需授权处理的待办 |
| 投诉处理周报 | 统一投诉工单 | 件数、分类、响应/解决时效、未决和超时清单 |

报告先由确定性查询生成指标，再由模型对**已计算事实**做摘要。报告保存统计起止、时区、数据快照时间、生成版本、来源记录数量和状态；数据不足时明确说明。自动任务与手动生成共用同一服务，幂等键由报告类型、时间窗和版本组成。心理报告的个人明细只能在授权页面查看，不应进入普通管理层周报。

## 4. 数据设计与迁移

现有数据库设计列出 `customer_info`、`customer_judgement`、`judgement_rule`、`course_project`、`lecture_event`、`faq`、`event_signup`、`knowledge_vector`、`intention_customer`、`employee_daily_report`、`complaint_feedback`、`student_score`、`onboarding_knowledge`、`student_admin_service`、`mental_health_profile`、`mental_warning`、`after_sales_ticket`、`student_knowledge_vector`、`report_config`、`report_record`。开发时以迁移脚本管理建表、索引和回滚；应用层统一 UTC 存储时间，展示时按用户时区转换。

**建议补充的结构（须评审）：**

| 对象 | 建议补充 | 用途 |
|---|---|---|
| 所有业务表 | 创建/更新人、版本号或状态变更日志、软删除/归档策略 | 审计和并发控制 |
| `customer_judgement` | 规则版本、逐产品结果、证据与复核状态 | 支持两个产品和可追溯研判 |
| `intention_customer` | 状态变更历史、独立跟进记录表 | 销售漏斗与转化路径统计 |
| `student_admin_service` | 审批人、审批时间、驳回原因、通知状态 | 请假审批闭环 |
| 投诉工单 | 类型、摘要、分派人、首次响应时间、结案时间、满意度 | 周报与超时预警 |
| `mental_warning` | 处理人、确认时间、关闭时间、升级状态 | 预警处置闭环 |
| `report_record` | 统计时间窗、数据快照、生成参数、失败原因 | 重跑与审计 |
| 新增通用表 | 用户/角色/数据授权、通知任务、外部同步游标、知识文档版本、审计日志 | 权限、消息和集成 |

原方案使用 JSON 存客户资料、报名信息和心理历史。需要频繁查询/统计的字段应规范化为独立列或子表；JSON 仅保留非关键扩展信息。向量字段是否与业务库共库，应在选型后确定，但文档元数据和访问控制必须可关联。

## 5. API 契约与待补接口

既有《接口设计文档》定义 `/api/v1` 统一响应及 21 个端点，可作为初版清单；开发前需补齐统一错误码、认证方式、分页、请求 ID、时间格式、幂等键、上传方式和鉴权矩阵。示例中的日期是样例数据，不代表当前活动或政策。

**必须修订的既有契约：**

1. `POST /customer/judge` 的 `source_content` 不适合直接承载 PDF/Excel 二进制文件；建议文本用 JSON，文件用上传接口返回 `file_id` 后发起研判，批量任务另设任务查询接口。
2. `POST /enterprise/daily-report` 当前 `voice_content` 是文字示例；语音应传 `file_id` 或音频上传结果，并明确转写确认步骤。
3. `POST /enterprise/nl2sql` 当前响应暴露 SQL；生产响应建议只给安全的结构化结果、查询解释及 trace ID。
4. `POST /enterprise/command` 当前仅有自然语言命令，缺少目标 ID、确认令牌与幂等键；建议采用“解析预览 → 用户确认 → 执行”两阶段。
5. 学生端以传入 `student_id` 查询或提交的示例，应改为从登录身份绑定并校验代理/监护授权。
6. `POST /report/generate` 的 `report_type` 仅有 daily/weekly，无法表示五种报告；需增加报告代码、统计时间窗与访问范围。

**建议新增接口组（路径为草案）：**

| 接口组 | 关键操作 |
|---|---|
| `/files`、`/customer/judge/batches` | 文件上传、批量研判、任务状态与错误下载 |
| `/enterprise/customers/{id}/follows` | 跟进记录追加与列表 |
| `/enterprise/organization`、`/enterprise/onboarding/ask` | 组织查询、新人指南问答 |
| `/enterprise/students/{id}/scores` | 成绩录入/查询 |
| `/enterprise/leave/{id}/decision` | 请假审批/驳回 |
| `/enterprise/tickets/{id}` | 投诉分派、跟进、结案 |
| `/student/leave/{id}`、`/student/tickets/{id}` | 本人申请和工单状态查询 |
| `/student/reminders`、`/student/chat` | 学业提醒设置、学生多场景对话 |
| `/notifications`、`/knowledge/documents` | 通知状态、知识导入/发布 |

以上补充接口解决现有清单无法完成的审批、通知、组织、成绩、批量研判和知识维护闭环；具体 URL 与字段以 OpenAPI 评审版为准。

## 6. 非功能与安全要求

- **身份和权限：**统一登录；基于角色加资源归属校验，学生、老师、管理层、访客分权。管理员也不应默认读取心理原文。
- **数据保护：**传输加密；个人信息、联系方式和心理数据按敏感级别加密/脱敏；日志与模型请求避免记录完整原文。明确保留期限、删除与备份恢复策略。
- **模型安全：**外部文本和知识库切片视为不可信输入；工具调用白名单、权限二次校验、输出结构校验。对注入、越权、虚构来源和错误政策做专项测试。
- **可用性与观测：**目标为 7×24 小时服务；监控 API 成功率/延迟、模型失败率、知识命中率、通知积压、外部系统同步延迟及报告任务失败。外部依赖故障时保留可解释的降级状态。
- **性能：**FAQ 秒级目标以缓存和标准问答为主；文件研判、长报告使用异步任务。查询列表必须分页，统计查询建立相应索引。
- **运维：**区分开发、测试、生产环境；配置和密钥由密钥服务管理；数据库迁移、知识库版本和提示词版本与应用发布关联；灰度发布并具备回滚路径。

## 8. 测试与验收矩阵

| 范围 | 核心用例 | 验收依据 |
|---|---|---|
| 客户研判 | 三种格式、批量、缺字段、规则升级、两产品分别判断 | 标注样本准确率 ≥95%；结果含规则版本和证据 |
| 客服 Agent | 七类意图、FAQ、政策失效、无依据拒答、推荐、重复报名 | 意图 ≥90%；FAQ 目标 ≤1 秒；知识问答 ≥95%；报名记录一致 |
| 企业助手 | 客户录入/状态、日报语音、越权查询、NL2SQL、歧义指令 | NL2SQL ≥90%；写操作有确认和审计，越权请求被拒绝 |
| 学生助手 | 请假审批通知、投诉结案、教务/CRM 故障、心理高风险 | 七场景意图 ≥90%；状态和通知可追踪；高风险预警到达授权人员 |
| 智能报告 | 日/周窗口、重复生成、数据缺失、权限隔离 | 指标可复算，摘要不超出事实，敏感数据按权限呈现 |
| 共性 | 身份冒用、提示注入、并发、重试、备份恢复 | 不发生越权写入；重试不产生重复记录；恢复演练通过 |

模型指标的样本集、标注规则、计时环境、失败阈值和验收签字人应在测试计划中固定。对心理风险场景须增加漏报专项评审和人工处置演练，不能只用总体准确率替代。

## 9. 待确认事项与风险

| 优先级 | 待确认事项 | 对开发的影响 |
|---|---|---|
| 高 | 《用户画像研判规则》、两个产品定义及标注样本 | 无法实现或验证真实研判 |
| 高 | 《公司信息》《公司业务》《留学政策》及政策维护人、更新时间 | 无法建立可信客服知识库 |
| 高 | CRM、教务、组织通讯录的接口契约、授权和测试环境 | 无法完成进度/学业/组织数据联调 |
| 高 | 班主任归属、心理预警接收人及处置流程 | 无法完成请假和高风险闭环 |
| 高 | `complaint_feedback` 与 `after_sales_ticket` 的统一事实源 | 可能出现双表状态不一致 |
| 中 | 五类报告的统计口径、时间区间、历史数据质量 | 同环比、满意度和时效可能无法准确计算 |
| 中 | 渠道形态、登录方式、语音供应商、通知渠道 | 影响前端、鉴权和消息实现 |
| 中 | SLA、数据保留期、敏感数据授权范围 | 影响部署容量和安全方案 |
