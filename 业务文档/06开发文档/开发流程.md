# 智能教育服务 Agent 平台落地实施步骤

---

## 阶段一：环境准备与基础搭建

**目标**：把四套基础设施跑起来。

1. **部署 MySQL**
   - 创建数据库 `education_agent`
   - 创建专用账号 `root`，密码是`12345`
   - 配置字符集为 `utf8mb4`，时区设为东八区

2. **部署 Dify**
   - 用 Docker Compose 拉起本地 Dify（含其自带的 PostgreSQL、Redis、Weaviate 等依赖）
   - 确认 Dify 控制台可访问（默认 80 或 3000 端口）
   - 确认 Dify API 端点可访问（默认 `/v1`）
   - 创建管理员账号，进入控制台

3. **搭建 FastAPI 项目骨架**
   - 创建 Python 虚拟环境，安装 FastAPI、uvicorn、SQLAlchemy、aiomysql、httpx、pydantic、apscheduler 等依赖
   - 建立项目目录结构（api / services / models / schemas / tasks / config）
   - 配置 `.env` 文件，写入 MySQL 连接信息和 Dify 地址占位

4. **搭建前端项目骨架**
   - 选定技术栈（Vue/React 均可），初始化项目
   - 配置四端路由（客户/员工/学生/管理）
   - 配置开发代理指向 FastAPI

**阶段产出**：MySQL可连、Dify 可访问、FastAPI 能启动、前端能启动。

---

## 阶段二：数据库设计与建表

**目标**：把方案里所有业务表建好，字段注释写清楚。

1. **设计并创建核心业务表**
   - 意向客户表、员工日报表、投诉反馈工单表、学生成绩表
   - 学生行政服务表、心理健康画像表、心理预警表
   - 活动与课程表、会话记录表、报告表
   - 操作审计表（NL2SQL 专用）

2. **为每张表编写清晰的字段注释**
   - 字段命名用业务语义化命名（如 `customer_status` 而非 `cs`）
   - 每个字段写中文注释，说明业务含义
   - 这是后续 NL2SQL 准确率的关键，注释越清晰，Dify 生成 SQL 越准

3. **初始化少量测试数据**
   - 每张表插几条样例数据，方便后续联调

4. **在 FastAPI 中编写 ORM 模型和 Schema 摘要生成器**
   - ORM 模型对应每张表
   - 写一个工具函数，能自动从 ORM 抽取“表名 + 字段名 + 类型 + 注释”的 Schema 摘要文本，供 NL2SQL 使用

**阶段产出**：数据库建好、ORM 模型写好、Schema 摘要可自动生成。

## 阶段三：Dify 应用与知识库搭建

**目标**：把 Dify 侧的 AI 能力全部配好。

1. **创建知识库并导入资料**
   - 公司知识库：导入《公司信息》《公司业务》，FAQ 整理成标准问答对导入
   - 留学政策库：导入《留学政策》
   - 海外生活库：导入生活指南资料
   - 升学项目库：导入课程表、硕博项目资料
   - 制度文件库：导入入职指南、规章制度，配置切片策略
   - 每个知识库配置混合检索，测试检索效果

2. **创建客服 Agent（Chatflow）**
   - 配置问题分类器，划分 7 大意图分支
   - 每个分支配置对应的知识库检索节点
   - 闲聊分支单独写年轻化 System Prompt，调高温度
   - 活动报名分支配置 HTTP 工具节点，指向 FastAPI 报名接口
   - 测试各意图分流是否正确

3. **创建员工智能助手（Chatflow）**
   - 配置问题分类器，划分知识问答类、数据操作类、闲聊类
   - 知识问答类走 RAG
   - 数据操作类接入 NL2SQL 工作流
   - 配置口述日报、指令解析等专用分支

4. **创建学生智能助手（Chatflow）**
   - 配置问题分类器，划分 7 大场景
   - 数据查询类接入 NL2SQL 工作流
   - 心理关怀分支配置心理分析工作流调用
   - 生活支持走海外生活知识库

5. **创建 NL2SQL 工作流（Workflow）**
   - 输入节点：接收“自然语言请求 + Schema 摘要 + 用户角色”
   - LLM 节点：System Prompt 要求严格基于 Schema 生成标准 SQL，输出结构化 JSON（SQL + 操作类型 + 涉及表 + 影响行数预估）
   - 输出节点：返回结构化结果
   - **关键**：System Prompt 中要写清楚“只生成 SELECT/UPDATE/INSERT，禁止 DROP/TRUNCATE/ALTER”，并要求字段名必须来自 Schema

6. **创建客户研判工作流（Workflow）**
   - 输入节点：接收客户信息文本
   - LLM 节点：加载《用户画像研判规则》作为 System Prompt，逐条匹配
   - 输出节点：返回结构化 JSON（是否匹配、匹配产品、理由）

7. **创建心理分析工作流（Workflow）**
   - 输入节点：接收学生消息 + AI 回复
   - LLM 节点：识别情绪标签、风险等级
   - 输出节点：返回结构化结果

8. **创建报告生成工作流（Workflow）**
   - 输入节点：接收报告类型 + 聚合数据
   - LLM 节点：按报告类型生成对应内容
   - 输出节点：返回报告文本

9. **为每个应用创建独立 API Key**
   - 记录到 FastAPI 的 `.env` 文件中

**阶段产出**：Dify 中 6 类应用全部配好，知识库可检索，NL2SQL 工作流可生成 SQL。

## 阶段四：FastAPI 后端核心开发

**目标**：把后端所有模块实现。

1. **实现 Dify 客户端封装**
   - 封装对话调用（支持流式和阻塞）
   - 封装工作流调用
   - 封装知识库检索调用
   - 统一超时、重试、错误处理

2. **实现 NL2SQL 四步链路**
   - 第一步：组装“自然语言 + Schema 摘要 + 用户角色”，调用 Dify NL2SQL 工作流
   - 第二步：安全校验模块（白名单、危险关键字过滤、行级权限注入、参数化提取、影响行数阈值）
   - 第三步：参数化执行 SQL，写审计表
   - 第四步：将结果回传 Dify，生成自然语言回复
   - **这是后端最核心的模块，需重点测试**

3. **实现各业务接口**
   - 对话接口：客服、员工、学生三个入口，透传 Dify 流式响应
   - 客户接口：录入、查询、状态更新、研判
   - 日报接口：提交、查询、汇总
   - 投诉接口：提交、跟进、状态更新
   - 学生业务接口：请假、成绩、进度
   - 报告接口：生成、查询
   - 活动接口：报名

4. **实现定时任务**
   - 主动待办推送：定时扫描未处理投诉、请假
   - 日报日汇总：每日定时生成
   - 周报生成：每周五定时生成
   - 心理预警扫描：定时检查中高风险

5. **实现鉴权与上下文**
   - 识别用户身份（客户/员工/学生/管理员）
   - 维护会话上下文
   - 按角色控制可访问接口和可访问表

**阶段产出**：FastAPI 所有接口可用，NL2SQL 链路跑通，定时任务可运行。

## 阶段六：联调与测试

**目标**：端到端跑通，修复问题。

1. **NL2SQL 重点测试**
   - 用各种自然语言问法测试生成 SQL 的准确性
   - 测试安全校验是否拦截越权、危险操作
   - 测试行级权限是否正确注入
   - 测试影响行数阈值和二次确认

2. **意图分流测试**
   - 测试三个助手的意图分类是否准确
   - 测试 fallback 是否生效

3. **业务闭环测试**
   - 请假：学生提交 → 班主任审批 → 学生收到通知
   - 投诉：学生提交 → 老师跟进 → 学生收到通知
   - 活动报名：对话中报名 → 写入数据库
   - 心理预警：对话触发 → 写入预警表 → 推送老师

4. **报告生成测试**
   - 五类报告分别测试生成效果
   - 测试定时触发和手动触发

5. **性能测试**
   - 并发对话测试
   - NL2SQL 链路耗时测试

**阶段产出**：所有业务流程端到端跑通，问题清单修复完毕。

## 关键提醒

1. **NL2SQL 是重中之重**，Schema 摘要的清晰度和 System Prompt 的质量直接决定准确率，建议在阶段三和阶段四反复打磨。
2. **字段注释必须写清楚**，这是 NL2SQL 准确率的基础。
3. **安全校验不能省**，白名单、行级权限、参数化、审计表四重机制必须全部到位。
4. **意图分类器要早测**，它决定所有请求能否正确分流，建议阶段三就重点测试。
5. **建议先做通一条最小闭环**（如学生请假全流程），再横向扩展其他业务，避免一次性铺开导致问题难定位。

按这 8 个阶段推进，每个阶段都有明确产出，可以边做边验证，最终形成覆盖客服、员工、学生、管理层四类角色的完整平台。
