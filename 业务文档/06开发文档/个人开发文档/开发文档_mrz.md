# 智能教育服务 Agent 平台技术方案（数据库 NL2SQL 版）

## 一、总体架构

采用 **前端 + FastAPI 后端 + 本地 Dify + 本地 MySQL** 的四层架构。

- **前端层**：面向四类角色，分别是客户/访客端、员工工作台、学生端、管理层看板。
- **FastAPI 后端层**：作为调度中枢，负责身份识别、意图路由、数据读写、Dify 调用、SQL 安全校验与执行。
- **Dify 层**：承载全部 AI 能力，包括对话编排、RAG 检索、Workflow 流程、意图分类、**NL2SQL 生成**。
- **MySQL 层**：承载所有业务数据持久化。

核心设计原则：**FastAPI 做编排与执行，Dify 做 AI 与 SQL 生成，MySQL 做持久化**。所有涉及数据库操作的场景，均由 Dify 将自然语言转换为 SQL，FastAPI 负责校验与执行。

---

## 二、NL2SQL 整体设计

NL2SQL 是本方案的核心机制，覆盖员工助手的数据查询、状态更新、学生业务综管、日报查阅、报告数据聚合等所有需要访问数据库的场景。

### 2.1 设计原则

**不采用“大模型直接生成 SQL 后无条件执行”的模式**，而是设计为 **“Dify 生成 SQL → FastAPI 安全校验 → 参数化执行 → 结果回写”** 的四步链路。原因是直接执行大模型生成的 SQL 存在三类风险：SQL 注入、越权访问（如员工查到不该看的数据）、误操作（如误删、误更新全表）。因此必须在 FastAPI 侧加一道安全闸门。

### 2.2 四步链路

**第一步：Dify 生成 SQL**

FastAPI 收到自然语言请求后，将请求连同**当前数据库 Schema 摘要**一起传给 Dify 的 NL2SQL 工作流。Schema 摘要包含所有表的表名、字段名、字段类型、字段注释、表关系。Dify 工作流中配置专门的 System Prompt，要求大模型严格基于 Schema 生成标准 SQL，并输出结构化结果（SQL 语句 + 操作类型 + 涉及表名 + 预估影响行数）。

**第二步：FastAPI 安全校验**

FastAPI 收到 Dify 返回的 SQL 后，执行多层校验：

- **白名单校验**：SQL 中涉及的表必须在该用户角色的可访问表白名单内。例如员工不能访问心理预警表，学生只能访问自己的数据。
- **操作类型校验**：查询类操作（SELECT）直接放行；更新类操作（UPDATE/INSERT）需校验字段合法性；删除类操作（DELETE）默认禁止，需走审批流程。
- **危险关键字过滤**：拦截 DROP、TRUNCATE、ALTER、GRANT 等危险语句。
- **行级权限注入**：自动在 WHERE 条件中注入用户身份限制。例如学生查询时自动追加 `AND student_id = 当前用户`，员工查询时自动追加部门限制。
- **参数化处理**：将 SQL 中的字面量提取为参数，使用参数化查询执行，彻底杜绝注入。
- **影响行数预估**：更新类操作若预估影响行数超过阈值（如超过 100 行），需二次确认。

**第三步：参数化执行**

通过校验的 SQL 由 FastAPI 通过异步数据库连接执行。查询类返回结果集，更新类返回影响行数。执行日志（谁、何时、什么 SQL、影响多少行）全部记录到操作审计表。

**第四步：结果回写与自然语言化**

执行结果返回给 Dify，由 Dify 将结构化结果转换为自然语言回复（如“查到张三最近 3 条跟进记录，分别是……”），再返回给前端展示。这样用户看到的是自然语言，而不是原始数据表。

### 2.3 NL2SQL 覆盖的场景

- 员工查询意向客户档案与跟进记录
- 员工更新客户流转状态
- 员工查询与汇总团队日报
- 员工查询组织架构与同事联系方式
- 员工处理学生成绩录入与查询
- 员工审批请假申请
- 员工跟进投诉反馈
- 学生查询自己的请假状态、成绩、投诉进度
- 管理层查询各类统计数据
- 报告生成前的数据聚合

所有场景统一走同一套 NL2SQL 链路，只是 Schema 摘要和权限白名单按角色不同而不同。

## 三、Dify 应用与知识库规划

在 Dify 中需要创建六类应用：

1. **客服 Agent**（Chatflow）：公司信息咨询、业务查询、留学政策查询、课程推荐、活动报名、FAQ、闲聊七大场景。
2. **员工智能助手**（Chatflow）：客户录入、客户查询、状态更新、口述日报、日报查阅、组织架构查询、入职指引、学生业务综管八大场景。**其中数据查询与操作类意图，路由到 NL2SQL 工作流**。
3. **学生智能助手**（Chatflow）：行政服务、心理关怀、售后反馈、学业考务、进度追踪、生活支持、增值转化七大场景。**其中数据查询类意图，路由到 NL2SQL 工作流**。
4. **NL2SQL 工作流**（Workflow）：接收自然语言 + Schema 摘要，生成 SQL + 操作类型 + 涉及表 + 影响行数预估。
5. **客户研判**（Workflow）：根据《用户画像研判规则》判断客户来源是否符合两个产品要求。
6. **报告生成**（Workflow）：生成五类智能报告。

知识库规划五套：公司知识库、留学政策库、海外生活库、升学项目库、制度文件库。知识库用于 RAG 检索类问答，NL2SQL 工作流用于数据库操作类请求，二者在 Chatflow 中通过意图分类器分流。

**意图分流逻辑**：Chatflow 中的问题分类器将用户意图分为三类——知识问答类（走 RAG）、数据操作类（走 NL2SQL）、闲聊类（走人设 Prompt）。数据操作类意图进入 NL2SQL 分支，由 Dify 生成 SQL 后回调 FastAPI 执行。

## 四、核心业务逻辑

### 4.1 客服 Agent

客户发起对话后，FastAPI 转发到 Dify 客服 Chatflow。Chatflow 完成意图识别、知识库检索、回复生成。活动报名意图通过 HTTP 工具节点回调 FastAPI 报名接口，FastAPI 通过 NL2SQL 链路将报名信息写入活动表。对话结束后 FastAPI 根据意图标签决定是否额外持久化留资信息。

### 4.2 企业智能助手

**意向客户录入**：员工语音或文字提交，FastAPI 调用 Dify 工作流结构化解析，解析结果通过 NL2SQL 链路写入客户表。

**意向客户查询与状态更新**：员工自然语言提问，走 NL2SQL 四步链路。查询时自动注入部门权限；更新时校验字段合法性并记录审计日志。

**口述日报**：员工语音转文字提交，Dify 工作流提取核心进展、关键产出、潜在风险，通过 NL2SQL 写入日报表。

**管理日报查阅**：管理层查询时走 NL2SQL，自动注入部门范围限制，FastAPI 聚合后返回前端。

**组织架构查询与新人入职指引**：走制度文件库 RAG 检索。

**学生业务综管**：成绩录入查询、请假审批、投诉跟进，全部通过 NL2SQL 链路完成。请假审批指令（如“同意张三请假”）由 Dify 解析出意图和参数，生成 UPDATE 语句，FastAPI 校验后执行。

**主动待办推送**：FastAPI 定时任务定期走 NL2SQL 查询投诉表、请假表中未处理事项，主动推送给对应员工。

### 4.3 学生智能助手

**行政服务**：学生提交请假，通过 NL2SQL 写入行政服务表，推送班主任，班主任审批后 NL2SQL 更新状态，回调通知学生。

**心理关怀**：每轮对话结束后 FastAPI 异步调用 Dify 心理分析工作流，识别情绪标签和风险等级。中高风险通过 NL2SQL 写入心理预警表并推送老师。

**售后反馈**：学生提交投诉，Dify 工作流生成工单摘要，通过 NL2SQL 写入投诉表。处理完毕后自动通知学生。

**学业考务**：FastAPI 对接教务系统 API 拉取 DDL、考试时间，通过 NL2SQL 写入本地缓存表，支持学生查询和提醒。

**进度追踪**：FastAPI 打通 CRM 或申请系统，学生查询时走 NL2SQL，自动注入 `student_id` 限制。

**生活支持**：走海外生活知识库 RAG 检索。

**增值转化**：Dify 识别升学意向，结合画像生成推荐话术。

### 4.4 客户研判

文本直接传入 Dify 工作流；PDF 由 Dify 文档提取器处理；Excel 先由 FastAPI 转文本。Dify 加载《用户画像研判规则》作为 System Prompt，逐条匹配后输出结构化 JSON（是否匹配、匹配产品、匹配理由）。FastAPI 校验格式后，通过 NL2SQL 写入客户表并返回前端。

### 4.5 智能报告

五类报告统一通过 Dify 工作流生成。**数据聚合阶段全部走 NL2SQL 链路**：FastAPI 将“聚合意向客户新增数量及同环比”“聚合本周全员日报”“聚合本周心理预警数据”“聚合本周投诉处理数据”等自然语言请求传给 Dify，Dify 生成聚合 SQL，FastAPI 校验执行后返回结果集，再传给报告生成工作流生成 AI 洞察。

报告触发方式：手动触发（前端按钮）、定时触发（日汇总每日、周报每周五）、事件驱动（投诉状态变化触发即时摘要）。

## 五、数据表设计概览

MySQL 中需建立的核心表：

- **意向客户表**：客户基本信息、跟进记录、当前状态、来源类型、研判结果。
- **员工日报表**：汇报内容、提交时间、所属部门、结构化摘要。
- **投诉反馈工单表**：投诉详情、处理状态、跟进人、AI 摘要、满意度。
- **学生成绩表**：各科成绩、录入时间。
- **学生行政服务表**：请假、考务申请单、审批状态。
- **心理健康画像表**：情绪标签、分值、历史波动。
- **心理预警表**：预警原因、风险等级、跟进状态。
- **活动与课程表**：时间、地点、报名方式、报名记录。
- **会话记录表**：用户 ID、会话 ID、意图标签、消息内容。
- **报告表**：报告类型、内容、时间范围、生成时间。
- **操作审计表**：操作人、角色、原始请求、生成 SQL、执行结果、影响行数、执行时间。

其中**操作审计表是 NL2SQL 链路的关键配套表**，所有通过 NL2SQL 执行的数据库操作都必须记录，用于追溯、复盘和风险排查。

每张表在设计时需提供**清晰的字段注释**，因为字段注释会被抽取进 Schema 摘要，直接影响 Dify 生成 SQL 的准确性。字段命名建议采用业务语义化命名（如 `customer_status` 而非 `cs`），减少大模型理解成本。

## 六、前端设计要点

前端按四端分离：

- **客户/访客端**：客服对话窗口、活动报名入口。
- **员工工作台**：客户管理、日报提交、待办列表、指令输入框。
- **学生端**：对话助手、请假提交、进度查询、投诉入口。
- **管理层看板**：报告看板、团队日报汇总、心理预警面板。

对话流式体验通过 SSE 实现，FastAPI 透传 Dify 流式响应。员工工作台的指令输入框支持语音和文字，返回结果以结构化卡片展示。对于涉及数据更新的操作，前端展示“待确认”卡片，员工确认后 FastAPI 才执行 SQL，形成人机协同的二次确认机制。

## 七、部署方案

本地部署采用 Docker Compose，包含四个容器：Dify 服务、MySQL 服务、FastAPI 服务、前端静态托管。

环境变量统一管理 MySQL 连接信息、Dify 基础地址、各应用 API Key。Dify 中每个应用独立 Key。NL2SQL 工作流的 System Prompt 中需注入完整 Schema 摘要，Schema 变更时同步更新 Prompt。

---

## 八、关键风险与应对

- **NL2SQL 生成错误 SQL**：FastAPI 侧白名单校验 + 危险关键字过滤 + 影响行数阈值 + 二次确认。
- **越权访问**：行级权限自动注入 + 角色可访问表白名单。
- **SQL 注入**：参数化执行，字面量全部提取为参数。
- **误操作**：DELETE 默认禁止，UPDATE 超阈值需确认，所有操作记录审计表。
- **知识库检索不准**：优先使用 Q&A 对，配置混合检索。
- **意图识别错误**：Chatflow 增加确认分支，无法识别时 fallback 人工。
- **心理风险误报**：多级阈值，低风险仅记录，中高风险推送。
- **Dify 响应超时**：合理超时 + 流式渐进渲染。
- **并发压力**：FastAPI 异步 + MySQL 连接池 + Dify worker 扩展。

---

**总结**：本方案以 NL2SQL 为核心数据访问机制，所有数据库操作统一走“Dify 生成 SQL → FastAPI 安全校验 → 参数化执行 → 结果自然语言化”四步链路。Dify 承担 AI 能力（对话、RAG、NL2SQL、报告、研判），FastAPI 承担编排、安全校验与执行，MySQL 承担持久化。整个平台覆盖客服、员工、学生、管理层四类角色，形成从获客、服务、管理到决策的完整闭环，同时通过白名单、行级权限、参数化、审计表四重机制保障数据安全。
