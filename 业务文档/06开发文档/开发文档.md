# 开发文档

> 本文根据当前仓库中的需求拆解、五份需求文档、开发设计、接口设计、数据库设计及《NL2SQL总结》整理，供项目启动、开发排期、联调和验收使用。当前仓库以项目文档为主，尚未发现应用程序源代码、部署配置或测试代码；因此本文描述建议的实现步骤，不代表已有技术栈或能力已经落地。

## 1. 项目目标与范围

建设一套面向潜在客户、企业员工和留学生的智能业务系统，覆盖五个业务模块：

1. **客户研判**：接收文本、PDF、Excel等客户资料，解析字段，按甲方提供的画像规则分别判断两个产品的匹配情况，并输出可复核结论。
2. **客服Agent**：支持公司信息、业务、留学政策、课程推荐、活动报名、FAQ和闲聊；知识问答应基于已审核资料，活动报名需写入业务数据。
3. **企业智能助手**：支持意向客户及日报管理、组织架构与新人指引、学生成绩/请假/投诉业务，以及安全的自然语言查询和指令处理。
4. **学生智能助手**：支持请假、心理关怀与预警、售后工单、学业提醒、留学进度、海外生活问答和升学项目推荐。
5. **智能报告**：生成客户经营分析、员工日报日/周报、学生心理健康周报和投诉处理周报。

建议采用分层模块化服务：接入/API层、业务应用层、AI能力层（意图识别、RAG、语音转写、研判、NL2SQL、摘要生成）、数据层（关系型数据库、向量检索、文件存储）和任务调度层。先按模块边界实现清晰的服务接口，是否拆分微服务应在技术选型和部署规模明确后决定。

## 2. 开发原则与关键边界

- **业务规则优先于模型判断**：客户研判应把甲方规则结构化、版本化；模型负责资料提取或解释，最终判定依据必须可追溯到具体规则。缺少信息时返回“待补充/需人工复核”，不得猜测。
- **知识问答可追溯**：RAG回答关联来源文档、更新时间和片段；检索不到可靠依据时明确告知并转人工/引导咨询。留学政策等时效内容需有责任人和更新日期。
- **AI不直接执行任意数据库操作**：NL2SQL采用只读账号、表/字段白名单、SQL解析校验、强制行数上限、超时和用户数据权限过滤；写操作只能映射到明确的业务命令/API，执行前确认对象和影响。
- **身份和权限贯穿全链路**：区分访客、学生、员工、班主任、管理员等角色；按本人、班级、部门等范围授权。心理健康数据和投诉信息应最小化访问、加密传输与存储，并记录访问/处置审计。
- **高风险心理事件由人接管**：模型输出仅作风险提示，不作为诊断。高危命中后走经业务方确认的通知与人工响应流程，保存必要证据和处置状态；面向学生展示合适的求助指引。
- **外部系统采用适配器**：教务、CRM、申请系统、消息渠道均通过适配层接入，明确鉴权、字段映射、超时、重试、幂等和降级策略；本项目不替代CRM/教务系统本身。

## 3. 建议实施阶段

### 阶段0：需求澄清与技术方案

1. 召开业务确认会，锁定本期范围、用户角色、端/渠道、两个研判产品的规则、外部系统和数据责任人。
2. 统一实体和状态定义：客户/学生/员工唯一标识、客户生命周期、请假审批状态、投诉状态、风险等级、报告周期及时间时区。
3. 确认部署环境、语言/框架、关系库与向量库、模型服务、对象存储、消息渠道、日志监控、密钥管理和网络要求。仓库目前未提供这些选择，不应在编码时默认某个产品。
4. 将需求文档中的接口示例升级为正式API契约：字段类型、必填/可空、分页、错误码、鉴权、幂等键、时间格式、文件上传限制及版本策略。
5. 制定样本集和验收口径，尤其是研判准确率、意图识别、RAG正确性、NL2SQL准确率、心理预警漏报/误报和响应时限。

**阶段交付**：经确认的需求基线、技术选型、数据字典/API契约、权限矩阵、风险处置流程、验收样本集和迭代排期。

### 阶段1：基础工程与数据底座

1. 建立项目代码结构、配置分环境、数据库迁移、API统一响应和错误处理、认证授权、审计日志、健康检查与基础监控。
2. 按数据库设计落表并补齐公共字段：主键、创建/更新时间、软删除或归档策略、数据来源、租户/组织范围（如适用）、版本号及必要索引/唯一约束。
3. 建立文件上传与解析流水线：文件类型/大小校验、病毒扫描（按部署要求）、解析状态、失败重试、原件访问权限和保留期限。
4. 建立模型/向量检索调用封装、Prompt版本管理、超时与限流、成本和调用日志。敏感原文不得无控制地写入日志或第三方模型。
5. 实现测试/演示数据和迁移回滚方案；为关键业务数据准备备份与恢复演练计划。

**阶段交付**：可运行的服务骨架、数据库迁移、登录/权限基础、文件和AI基础设施、运行手册初稿。

### 阶段2：客户研判与客服Agent

#### 2.1 客户研判

1. 与业务方取得《用户画像研判规则》及两个产品的正式定义，拆为规则项、阈值、优先级、适用产品、缺失信息处理和版本生效时间。
2. 实现文本/PDF/Excel解析器，保留原始文件引用；将解析字段和来源页码/单元格关联，支持人工纠正解析结果。
3. 实现规则引擎：按产品分别输出匹配状态、命中/未命中规则、证据、置信/完整性提示和人工复核标志；保存规则版本和研判快照。
4. 实现单条与批量研判API、结果查询、失败重试和人工复核入口；对规则更新提供版本发布与回滚。
5. 用业务标注样本评估准确率和字段解析质量，分析误判并形成回归样本。

#### 2.2 客服Agent

1. 接入并清洗《公司信息》《公司业务》《留学政策》、FAQ、课程和活动资料；标注来源、有效期、适用地区及审核人。
2. 构建文档切分、向量化、检索、重排、引用和内容更新流程；FAQ可优先精确/语义匹配，知识问答走RAG。
3. 实现七类意图路由与兜底澄清；推荐逻辑使用明确的学历/国家/项目条件，不满足时先追问。
4. 实现客服会话API、活动列表、活动报名、FAQ查询；报名时校验活动状态/名额（如有）、重复报名和个人信息授权。
5. 对政策问答展示来源及更新时间；过期或无资料时拒答/转人工，不凭模型记忆给出确定性政策结论。

**阶段交付**：研判闭环、客服问答和报名闭环、知识维护流程、两模块验收报告。

### 阶段3：企业智能助手

1. 实现意向客户录入、详情/跟进记录查询、状态更新以及员工日报录入和管理查阅。
2. 组织架构和新人指引采用可维护数据/知识库接入，按员工权限展示联系方式和制度资料。
3. 接入语音转写（若确定渠道和服务商），与文字输入统一进入字段抽取和确认流程；日报提交前允许员工查看、修改。
4. 实现学生成绩、投诉反馈和请假业务所需CRUD/查询接口，明确与学生助手共用表还是通过服务接口访问，避免两套数据源。
5. 实现NL2SQL只读链路：权限识别 → Schema/业务术语召回 → 生成SQL → AST/白名单校验 → 附加权限条件、LIMIT和超时 → 只读库执行 → 结果脱敏与自然语言总结。记录可审计的查询意图和SQL摘要。
6. 实现指令解析为结构化动作，并映射到白名单API；对审批、状态变更等操作先校验角色、对象和当前状态，必要时二次确认，保证幂等并记录操作者。
7. 实现待办轮询/事件触发与消息通知；消息失败可重试，避免重复提醒，并允许员工查询/关闭提醒。

**阶段交付**：企业助手业务接口、NL2SQL安全评审、指令操作审计、提醒闭环。

### 阶段4：学生智能助手

1. 实现请假申请、审批待办、审批结果通知和状态流转；对接企业端审批时共享统一业务接口。
2. 实现投诉/建议工单创建、分派、跟进、解决方案和学生通知；关键状态变更保留操作者与时间。
3. 实现心理情绪信号分析和预警记录；由业务方确认风险分级、通知对象、响应SLA、非工作时间流程、人工接管和误报复核机制后上线。
4. 接入教务数据并实现DDL/考试查询及提醒；接入CRM/申请系统查询留学进度。外部系统不可用时明确展示数据时间和降级提示。
5. 导入经审核的海外生活指南和升学项目资料，构建带引用的RAG；升学推荐需明确用户同意和营销频率限制。
6. 实现多意图路由、会话上下文、澄清问题和用户身份绑定；保护不同学生间数据隔离。

**阶段交付**：学生服务闭环、外部系统联调记录、心理风险安全评审和应急流程。

### 阶段5：智能报告

1. 明确五类报告定义：客户经营分析、员工日报日/周报、心理健康周报、投诉处理周报；确认统计周期、同环比口径、指标计算方式、可见角色与导出格式。
2. 先以SQL/规则生成可复算的指标和表格，再让模型对聚合数据做摘要、趋势解释和建议，避免模型自行编造数值。
3. 建立报告配置、定时任务、报告记录、失败重跑、生成时间和数据截止时间；防止重复生成。
4. 客户聚类、成交转化路径和流失归因等超出当前表结构的数据分析，须先补齐客户来源、触点、成交金额/时间、流失原因等数据字段和标注流程。
5. 心理报告优先输出群体趋势和需人工关注的匿名/最小必要信息，按严格角色授权查看个人级预警；避免不必要暴露敏感内容。

**阶段交付**：报告模板、指标口径、调度配置、报告权限和可追溯数据快照。

### 阶段6：联调、试运行与上线

1. 按端到端场景联调：文件研判、客服问答到报名、员工录入/查询/更新、学生请假审批通知、投诉闭环、心理预警处置、报告生成。
2. 验证功能、权限隔离、输入校验、并发/超时、外部系统异常、重复请求、审计、备份恢复和敏感数据脱敏。
3. 用业务确认的标注集评估准确率；测试集与提示词/规则调优集分开，报告样本量、指标算法和错误案例。
4. 先灰度给内部员工/小批学生使用，监测响应时间、失败率、模型成本、拒答/转人工率、误报漏报和用户反馈。
5. 完成上线检查、数据初始化、账号权限复核、告警联系人、回滚方案、客服/管理员培训和版本发布记录。

| 共享能力 | 认证授权、文件解析、模型适配、向量检索、通知、审计 | 统一错误处理、限流、监控、配置与密钥管理 |

## 5. 接口与数据实现注意事项

- 当前接口文档是示例级契约，编码前应补齐认证方式、权限、分页、排序、筛选、字段约束、错误响应、幂等、限流和审计要求。
- 文件上传接口应采用 multipart 或受控对象存储引用，不宜把PDF/Excel原文直接塞入普通JSON字段；明确最大大小、格式白名单和解析失败反馈。
- 活动/课程字段需补充状态、有效期、名额、创建/更新人；报名表应关联客户/活动并设置防重复策略。
- 客户跟进最好从单个长文本拆为跟进记录表，才能支持按时间查询、审计和报表；客户身份字段需定义唯一性和合并规则。
- 请假审批、投诉工单、心理预警需补齐处理人、状态变更时间、备注/处置记录、通知记录和幂等标识。
- 数据库中JSON字段仅用于扩展属性；常用于筛选、关联、统计的字段应拆列并加索引。外键、枚举、软删除和保留期限需根据所选数据库明确。
- 向量记录应保存文档版本、来源定位、更新时间、审核状态和删除标记；删除/替换文档时同步清理旧向量。
- NL2SQL对外返回结果不应泄露数据库凭据或不必要的原始SQL细节；应保留受控审计信息供管理员追查。

## 6. 验收与质量门槛

以下准确率指标来自现有需求文档；业务方须确认测试集规模、判定方法和上线门槛。技术验收还应覆盖安全和业务闭环。

| 范围 | 需求文档指标/验收点 | 实施验收方式 |
|---|---|---|
| 客户研判 | 规则研判准确率≥95%；文本/PDF/Excel解析；结构化输出；规则可更新 | 盲测标注集、字段抽取抽检、规则版本回放、人工复核 |
| 客服Agent | 意图识别≥90%；FAQ≤1秒；RAG准确率≥95%；报名入库；闲聊满意度≥85% | 七类意图样本、知识问答引用核查、响应计时、报名去重、用户问卷 |
| 企业助手 | 文字/语音录入查询更新；日报查阅；学生业务；NL2SQL≥90%；待办和指令闭环 | 角色用例、权限越权测试、SQL危险语句拦截、重复命令幂等、端到端审批 |
| 学生助手 | 七类路由≥90%；心理高危预警；工单/通知闭环；学业与进度查询；生活知识问答 | 业务路径验收、危机演练、人工响应确认、外部系统异常演练、引用核查 |
| 智能报告 | 五类报告齐全；日/周周期正确；趋势与归因有数据支持 | 核对指标SQL、抽查样本、调度重跑、访问权限和数据截止时间检查 |
| 全局质量 | 数据安全、可靠性、性能、可维护性 | 鉴权/隔离/脱敏/审计检查、备份恢复演练、压力和故障注入（按确认目标） |

心理风险识别不应用单一准确率指标替代安全评估；应同时衡量高危召回、误报处置负担、人工响应时间和未处理告警数，并由具备资质的业务负责人审核流程。

## 7. 当前资料中的待确认项与差异

1. **代码与技术栈**：仓库目前未提供应用源代码、依赖清单或部署说明；需要先确认语言、框架、模型、关系数据库、向量库和运行环境。
2. **研判规则**：未发现《用户画像研判规则》原件，也未见两个产品的名称/代码、条件和标注样本；这是客户研判开发和准确率验收的前置条件。
3. **外部数据**：公司信息、业务、留学政策、FAQ历史记录、新人指南、生活指南、升学项目资料，以及教务、CRM、申请系统接口资料均需业务方提供并指定更新责任人。
4. **模块范围差异**：开发设计将组织架构、新人指引、学生成绩等列入企业助手；接口文档覆盖不完整。学生需求还包含心理关怀、学业提醒、生活支持、升学推荐等，但接口文档尚无对应完整接口。
5. **数据模型差异**：企业助手设计包含投诉和成绩表，学生助手另有售后工单表；需决定统一工单/学生/请假模型还是通过服务接口共享，避免重复存储。意向客户字段目前是JSON加单一跟进文本，难以满足历史记录和分析需求。
6. **接口差异**：研判接口示例返回单一产品结果，但需求要求判断两个产品；需确认一次返回两个产品结果还是按产品分别请求。文件上传、审批回调、提醒、组织架构、语音、报告五种类别等接口也需补全。
7. **NL2SQL目标差异**：总结文档建议只读SQL和人审等安全能力，但接口示例返回SQL。需明确面向用户是否展示SQL；生产查询应限定白名单和数据范围，禁止模型执行写SQL。
8. **心理安全流程**：需明确风险等级定义、告警接收人、响应时限、非工作时间联系人、学生知情与隐私告知、数据保留和人工关闭规则。
9. **报告指标与数据缺口**：同环比周期、客户转化路径、成交价值、流失归因、心理群体指标和投诉满意度尚无统一计算口径，当前数据库字段也不足以支持全部分析。
10. **账号与权限**：需提供员工/学生/班级/部门身份源、角色职责、数据可见范围、管理员和审计员定义，以及账号注销和权限回收流程。

## 8. 建议的首批开发顺序

1. 先定技术栈、接口规范、统一身份/权限和数据字典。
2. 先完成基础工程、业务数据表和审计，再做确定性CRUD闭环。
3. 以客户研判（规则可拿到时）和客服Agent为首批AI场景，建立评测、知识更新和人工兜底流程。
4. 再做企业助手的录入/查询/更新、学生请假和投诉闭环；NL2SQL与自然语言写操作在权限和审计就绪后上线。
5. 心理预警在人工响应机制完成演练后开放；报告最后接入稳定数据并逐项核对指标。

该顺序可按团队并行能力调整，但共享数据模型、权限和外部接口契约应先冻结，避免多个模块各自定义同一业务对象。
