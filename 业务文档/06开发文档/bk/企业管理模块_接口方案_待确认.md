## 2. 范围与执行原则

本期覆盖：客户及跟进、员工日报、组织通讯录、新人指南、学生查询与成绩、请假审批、投诉处理、老师心理预警处置、待办通知、自然语言查询与操作。

1. NL2SQL 仅查询；所有新增、修改、审批、分派、作废和标记已读由固定业务服务执行。
2. 表单与自然语言入口复用相同业务服务、鉴权、状态校验及事务。
3. 学生端与企业端使用同一学生、申请、成绩、工单和预警；不复制可写业务表。
4. 待办从当前业务状态计算，不另建待办表。通知已读不等于事项完成。
5. 企业端不建设 CRM、教务、人事薪酬、通用工作流或完整入职任务系统。
6. 正式报告交给报告模块；客服的课程、活动、报名和会话记录仍由客服模块管理。

## 3. 通用接口契约

### 3.1 路径、身份与数据范围

基础路径为 `/api/v1/enterprise`。以下企业接口清单省略此前缀；`/student`、`/report` 路径在跨模块章节明确标为其他模块。

员工身份从认证上下文取得，员工已停用或离职时拒绝登录业务。正文中的目标负责人 ID 是业务参数，必须验证其有效性，不能替代真实操作身份。姓名、工号、学号和外部 ID 均不替代内部主键。

采用企业功能与数据库设计方案 4.1 的六个固定角色代码 `employee/consultant/manager/teacher/academic/admin`，接口分配详见第 12 节，最终由后端固定配置解释；当前 DDL 只约束 `role_codes` 为非空数组，没有校验这些代码。管理员的配置权限不自动等于全部业务数据权限。

| 场景 | 建议权限范围 |
|---|---|
| 普通员工 | 本人日报、允许公开的通讯录、授权知识 |
| 顾问 | 本人客户及跟进；部门主管按授权部门范围查看与分派 |
| 教务 | 功能角色、有效学生关系及课程范围同时满足才可录入/更正成绩 |
| 请假 | 具备审批功能且为当前 `reviewer_id`，同时检查有效学生关系 |
| 工单 | 当前处理人或具备该处理部门分派/管理权限的员工；检查投诉利益冲突 |
| 心理预警 | 单独配置处置权限及学生范围，不能仅凭“老师”或“主管”身份读取全部心理信息 |

默认主管范围仅包含本部门；是否含子部门作为固定配置显式开启。多角色分别计算功能与范围，不能任意拼接扩大权限。

### 3.2 请求与响应

- JSON 字段使用 `snake_case`；不直接序列化 ORM 全字段。
- 列表默认 `page=1,page_size=20`，`page_size` 最大 100；返回 `items/total/page/page_size`。排序字段白名单，默认时间与主键共同排序。
- 所有业务 ID 对外建议返回十进制字符串，避免前端大整数精度问题；后端严格验证后映射 BIGINT。
- 可变实体详情及写回结果统一返回整数 `version`。`knowledge_entry.version_no` 单独返回 `content_version`，避免与并发版本混淆。
- 写操作提交 `Idempotency-Key`，建议 UUID，统一限制 1～64 字符；重试保持不变。涉及业务状态或字段修改时，同时提交 `expected_version`。
- 无正文的草稿删除通过 `If-Match: "<version>"` 传递版本；其他业务删除均采用带原因的 POST 作废/归档接口。
- 查询、生成临时预览和知识问答不写业务事实，不要求业务幂等键。
- 时间输入带时区，输出 ISO 8601，数据库连接按 UTC；`report_date` 为上海时区工作日日期。

成功列表示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 20
  }
}
```

写操作响应在 `data` 中返回实体主键、`version`、实际业务状态、`operation_id` 和 `operation_status`。`operation_id` 映射 `operation_log.operation_log_id`；响应字段不要求数据库增加同名列。通知入队成功可以附带 `notification_status=queued`，不冒充已经送达。

### 3.3 业务码

| code | 含义 |
|---|---|
| 0 | 本次 API 请求已按契约处理；写入是否最终完成还需读取 `operation_status` |
| 400 | 参数、枚举、时间或必填条件错误 |
| 401 | 未登录、凭证失效 |
| 403 | 无功能权限或超出数据范围 |
| 404 | 对象不存在；需要隐藏存在性时，越权对象也按不存在处理 |
| 409 | 版本冲突、状态冲突、同幂等键不同参数、业务唯一键冲突 |
| 500 | 服务内部错误 |
| 502 / 504 | 外部依赖明确失败 / 超时；外部写入结果不明时按下述待核实契约返回 |

沿用项目现有业务异常 HTTP 200 + 业务码的风格，不在本模块单独切换协议；鉴权中间件与参数校验异常也应统一信封。上述新增业务码及参数校验处理尚未实现。

外部执行状态使用当前 `operation_log` 的 `processing/succeeded/failed/pending_external/unknown_external`。外部写入结果未确认时，可以 `code=0` 返回已受理回执，但必须明确 `operation_status=pending_external` 或 `unknown_external`，`message` 为“处理中/待核实”，不能显示“保存成功”。

## 4. 当前数据库对应与共享服务分工

| 功能 | 事实表/主键 | 版本列 | 历史或沟通记录 | 通知表（建议分工，待确认） |
|---|---|---|---|---|
| 组织员工 | `org_department.department_id`、`employee.employee_id` | `row_version` | `operation_log` | 必要时 `business_notification` |
| 客户跟进 | `customer_profile.customer_id`、`customer_followup.followup_id` | `row_version` | 跟进事实独立保存，变更历史进 `operation_log` | `business_notification` |
| 日报 | `employee_daily_report.daily_report_id` | `row_version` | `operation_log` | `business_notification` |
| 学生及关系 | `student_profile.student_id`、`student_staff_binding.binding_id` | `row_version` | `operation_log` | 按触发业务分流 |
| 成绩 | `student_score.score_id` | `row_version` | `operation_log` | 需要通知时 `business_notification` |
| 请假 | `student_admin_service.id`，且 `apply_type=leave` | `version` | `student_service_action`，业务类型 `administration`；企业写入另留操作回执 | `student_notification` |
| 投诉建议 | `service_ticket.ticket_id` | `row_version` | `service_ticket_record` 保存沟通；`operation_log` 保存变更和回执 | `business_notification` |
| 心理预警 | `mental_warning.id` | `version` | `student_service_action`，业务类型 `mental_warning`；企业写入另留操作回执 | `student_notification` |
| 知识 | `knowledge_entry.knowledge_id` | `row_version` | `operation_log`，正文版本为 `version_no` | 按需 |

以上通知与历史分工是针对当前并存表的方案选择，并非 DDL 已强制保证：

1. 一个逻辑通知只选择一个通知表，同一业务事件不得同时由两套发送器投递。工单统一使用 `business_notification`，不再向 `student_notification.business_type=ticket` 双写；该枚举暂时保留不使用。
2. 工单时间线只使用 `service_ticket_record`，不再向 `student_service_action.business_type=ticket` 重复写入同一条沟通。`operation_log` 仍可保存相应变更快照与幂等回执。
3. `student_service_action` 用于请假和心理处置的业务时间线；其 `event_key` 根据真实对象、动作和逻辑请求稳定生成。状态保持原业务枚举，不互相翻译成另一张表的状态。
4. 企业写操作以 `operation_log` 占用操作键、核对参数摘要并返回原回执；更新主表、追加必要处理记录和创建通知同一事务完成。
5. `student_admin_service.request_key/request_hash` 是原学生提交申请的幂等数据，审批或转派不得覆盖。审批幂等使用操作回执及处理事件键。
6. `reviewer_id`、`follower_id`、两张学生配套表的通用员工引用没有员工外键；必须在服务层验证员工存在、状态及授权。数据库有字段不代表关系约束已经完整。
7. 同一进程内可直接复用业务 service；分服务部署时提供可信内部 API。企业端不通过学生登录入口冒充学生执行操作。

统一收件箱返回 `source=business/student` 加 `notification_id`，联合标识一条通知，避免两表自增 ID 冲突。读取和标记已读时，根据来源核验真实接收员工。

## 5. 企业端业务接口清单

下表“参数”列列出业务重点；通用分页、身份、幂等、版本与响应沿用第 3 节。接口均为拟定，不表示已经实现。P0 为基础业务与跨端闭环，P1 为智能能力。

### 5.1 当前员工与通讯录（P0）

| 编号 | 方法 | 路径 | 功能、参数及返回重点 |
|---|---|---|---|
| ORG-01 | GET | `/me` | 返回 `employee_id/full_name/department_id/role_codes` 及受控功能列表 |
| ORG-02 | GET | `/departments` | 参数 `parent_department_id/keyword/tree`；返回部门职能、主管及组织树，不暴露后台身份字段 |
| ORG-03 | GET | `/employees` | 参数 `keyword/department_id/position_title`；返回有效员工通讯录 |

### 5.2 客户与跟进（P0）

| 编号 | 方法 | 路径 | 功能、参数及返回重点 |
|---|---|---|---|
| CUS-01 | POST | `/customer` | `full_name/phone/education_level/target_country_code/source_channel/source_reference`；创建客户，归属按身份或授权分派确定；返回 `customer_id/customer_no/status/version` |
| CUS-02 | GET | `/customer` | 按 `keyword/status/employee_id/department_id/is_archived` 筛选；默认排除归档 |
| CUS-03 | GET | `/customer/{customer_id}` | 客户详情、当前负责人和最近跟进信息；完整跟进分页另查 |
| CUS-04 | PATCH | `/customer/{customer_id}` | 修改姓名、联系方式、学历、意向国家等白名单资料；不混改状态、负责人或外部权威配置 |
| CUS-05 | PUT | `/customer/{customer_id}/status` | `status/lost_reason/change_reason/expected_version`；按状态规则更新 |
| CUS-06 | POST | `/customer/{customer_id}/transfer` | `employee_id/department_id/change_reason/expected_version`；分派或移交，验证负责人和部门关系 |
| CUS-07 | POST | `/customer/{customer_id}/archive` | `change_reason/expected_version`；归档，保留销售状态和全部历史 |
| CUS-08 | POST | `/customer/{customer_id}/followups` | `followup_at/channel/content/summary/next_followup_at/followup_status`；追加跟进，实际跟进人取登录身份 |
| CUS-09 | GET | `/customer/{customer_id}/followups` | 按时间、跟进状态分页；返回 `followup_id` 与 `version` |
| CUS-10 | PATCH | `/customer/{customer_id}/followups/{followup_id}` | 更正内容或调整/完成/取消跟进安排；`change_reason/expected_version`；校验跟进属于路径客户 |

规则：

- 客户状态建议为 `new → contacting → qualified → signed`，售前可转 `lost`；恢复跟进需要原因，签约后的解约退款不冒充售前流失。
- `phone` 是 API 输入字段，由后端加密并生成查重标记；不接收客户端提供的 `phone_ciphertext/phone_lookup_token`。默认输出脱敏电话，授权详情可返回必要明文。
- 手机号相同只提示重复候选，不直接合并；确认重复候选时返回的资料也须受权限限制。
- 录入默认 `status=new`，`customer_no` 由后端生成。`authority_source` 按后端集成配置决定，普通员工不能自行切换。
- 待跟进须有 `next_followup_at`；完成或取消后移出待办。跟进计划归客户当前负责人，历史实际跟进人不随移交改写。
- 归档不代表完成已有请假或工单；客户未完成跟进安排需先明确取消/移交，归档后禁止新增安排。恢复归档不纳入首期，需业务确认后另加动作。
- CRM 权威模式先通过固定适配器写回；成功确认后更新快照；结果不明返回待核实。

### 5.3 员工日报（基础 P0，整理与汇总 P1）

| 编号 | 方法 | 路径 | 功能、参数及返回重点 |
|---|---|---|---|
| DAY-01 | POST | `/daily-report/prepare` | `report_date/text`；整理为 `proposed_content/ai_summary`，仅临时预览（P1） |
| DAY-02 | POST | `/daily-report` | `report_date/submitted_content`；本人首次正式提交，后端确定员工与部门快照 |
| DAY-03 | GET | `/daily-report` | `start_date/end_date/employee_id/department_id/status`；本人或授权部门查询，默认仅有效正式日报 |
| DAY-04 | GET | `/daily-report/{daily_report_id}` | 正式内容、摘要、日期、提交部门、提交时间及版本 |
| DAY-05 | PATCH | `/daily-report/{daily_report_id}` | 本人修订 `submitted_content/change_reason/expected_version`；保留旧内容，重新生成或清空旧摘要 |
| DAY-06 | POST | `/daily-report/{daily_report_id}/void` | `change_reason/expected_version`；本人或具备纠错权限人员作废，不物理删除 |
| DAY-07 | POST | `/daily-report/summary` | `start_date/end_date/department_id`；返回授权正式日报摘要、来源 ID、数据时间，不保存正式报告（P1） |

同一员工同一天只能一条记录。重复日期新建返回 409；修订通过 DAY-05。已作废日报再次提交也通过 DAY-05，明确恢复为 `submitted` 并记录原因，避免唯一键冲突。日报日期与归属员工不允许在修订中随意改写；误日期通过作废原记录后按正确日期提交处理。

草稿、转写和 AI 整理在确认前不写日报表；生成摘要不能覆盖员工正式内容。部门变更后读取提交部门快照，修订时按当前设计刷新该快照并记录旧值。日报汇总不等于正式报告生成。

| LEA-03 | POST | `/leave/{apply_id}/decision` | `decision=approved或rejected/comment/expected_version`；当前审批人审批，驳回意见必填 |
| LEA-04 | POST | `/leave/{apply_id}/assign` | `reviewer_id/change_reason/expected_version`；有权分派者处理首次分派或转派 |
| LEA-05 | GET | `/leave/{apply_id}/records` | 查询 `student_service_action` 的 `administration` 时间线，仅该申请及授权范围 |

5. 审批结果和 `student_notification` 在同一事务入队；`student_service_action` 追加 approve/reject/assign 记录。
6. 取消状态为 `cancelled`，由学生端撤回待审批申请；不通过企业端 DELETE 删除申请。
7. 当前表没有请假附件字段，本期接口不承诺附件上传或下载。若需要证明附件，需另行确认表结构或公共附件服务方案。

### 5.6 投诉与建议（P0）

| 编号 | 方法 | 路径 | 功能、参数及返回重点 |
|---|---|---|---|
| TIC-01 | GET | `/tickets` | `student_id/ticket_type/category_code/status/employee_id/handling_department_id/overdue` |
| TIC-02 | GET | `/tickets/{ticket_id}` | 当前工单、解决方案、处理员工、SLA 时间、版本和处理轮次 |
| TIC-03 | POST | `/tickets/{ticket_id}/assign` | `employee_id/handling_department_id/change_reason/expected_version`；分派或转派 |
| TIC-04 | POST | `/tickets/{ticket_id}/follow` | `record_type=response或note/content/visibility/expected_version`；追加回应或内部备注 |
| TIC-05 | POST | `/tickets/{ticket_id}/resolve` | `solution/expected_version`；提交解决方案，进入 `awaiting_student`，通知学生 |
| TIC-06 | GET | `/tickets/{ticket_id}/records` | 查询授权处理时间线，按轮次分页，不通过通用 SQL 暴露内部备注 |

建议状态规则：

```text
open → assigned → processing → awaiting_student → closed
                    ↑                 ↓ 学生表示未解决
                    └──────── reopened
```

- 初次分派由 `open` 进入 `assigned`；处理中转派保持 `processing`，不能任意重置为初始状态。关闭工单不允许直接转派或追加解决动作。
- 首次实际处理由人工 `response` 进入 `processing`；`note` 仅追加内部说明，不算首次有效人工回应，不填写 `first_response_at`。学生可见回应才触发相应通知。
- `resolve` 只允许 `processing`，必须有解决方案，设置 `resolved_at`，不能直接冒充学生确认并写入 `closed_at`。
- 学生确认、评价与重开由学生模块处理同一工单；重开增加 `reopen_count`，重新计算本轮解决截止时间，处理记录 `cycle_no=reopen_count+1`。本期不自动超时关闭。
- `service_ticket_record` 追加保存，修正说明通过新记录表达；系统生成 `record_key`、真实操作者和目标状态，不接受任意客户端填写这些字段。
- `response_due_at/resolution_due_at` 为当前表必填字段；学生工单创建服务必须取得统一 SLA 配置后才能正确创建。具体时长待确认，首期按连续时间计算。
- 现有表没有“学生撤销”状态，本期不沿用旧学生方案中的删除/撤销投诉接口，需另行确认状态设计。

| 编号 | 方法 | 路径 | 功能、参数及返回重点 |
|---|---|---|---|
| AI-01 | POST | `/chat` | `message/conversation_id`；返回意图、回答、澄清候选或待确认预览；不隐式执行写操作 |
| AI-02 | POST | `/nl2sql` | `query`；仅返回授权结构化查询结果、字段说明及数据时间，不默认返回 SQL |
| AI-03 | POST | `/command` | `command/conversation_id`；解析注册动作、具体对象与字段，返回确认预览或缺失项 |
| AI-04 | POST | `/command/confirm` | `confirmation_token` 加幂等键；校验预览、身份、权限、版本及参数后执行固定业务服务 |
| AI-05 | POST | `/audio/transcriptions` | `multipart/form-data` 临时音频；返回转写文本，不直接创建客户或日报 |

若公共层已有语音接口则复用其地址，不重复实现 AI-05。原始音频只临时处理，不写客服会话表或新增录音表。企业对话使用受账号约束的外部会话或短期上下文，不直接复用标注为客服访客的 `chat_session/chat_message`。

写入流程为：输入 → 提取动作与参数 → 澄清重名/缺项 → 预览 → 员工确认 → 再鉴权与版本校验 → 固定服务执行 → 真实回执。模型只能匹配注册动作，例如 `create_customer/change_customer_status/submit_daily_report/correct_score/approve_leave/resolve_ticket`，不能指定任意表和 SQL。

确认凭证由后端短期签名，绑定真实账号、动作、目标 ID、业务参数摘要、对象版本和失效时间；不新增命令表。执行幂等键由逻辑确认凭证稳定派生或绑定，换一个请求头也不能重复执行同一预览；过期、参数变化或版本变化需要重新预览。已成功操作的同键重试优先返回原回执。

NL2SQL 必须校验实际 SQL 语法树、字段白名单和服务端行范围，使用只读数据库账号并限制扫描范围、返回行数与执行时间；拒绝多语句、写入、副作用函数、任意日志/通知/心理信息查询。首版建议只查询单个受控视图，复杂关联使用开发者固定视图或查询服务。当前 DDL 未创建这些视图，需要后续实施时补充，不声称已经具备。

`app/services/nl2sql_service.py` 当前仅用 `startswith("select")`，并使用通用数据库引擎，也未接收可信员工范围；不能直接挂载为满足本方案的业务查询入口。公共查询服务最终地址尚未在仓库找到，企业入口应复用公共客户端，不额外开发一套 SQL 生成器。固定表单查询与事务内部校验用确定性查询，不依赖模型生成 SQL。

```json

```

### 7.4 自然语言预览与确认

请求 `POST /command`：

```json
{
  "command": "同意张三的请假申请"
}
```

存在重名或多条待审批申请时返回 `status=needs_clarification` 和授权候选，不生成可执行确认凭证。目标唯一且信息完整时，示例 `data`：

```json
{
  "status": "awaiting_confirmation",
  "action": "approve_leave",
  "target": {"apply_id": "201", "student_name": "张三"},
  "parameters": {"decision": "approved"},
  "expected_version": 3,
  "confirmation_token": "<后端签名的短期凭证>",
  "expires_at": "<带时区的失效时间>"
}
```

确认时 `POST /command/confirm`，携带稳定幂等键及 `confirmation_token`，不再次由模型选择对象或生成更新语句；确认完成后返回与固定审批接口相同的业务回执。

`GET /notifications` 的某条站内消息：

```json

  "notification_id": "501",
  "business_type": "administration",
  "business_id": "201",
```

## 8. 与其他模块的接口边界

| 模块 | 保留/复用接口能力 | 企业端协作规则 |
|---|---|---|
| 学生请假 | `/api/v1/student/leave` 的提交、本人查询、撤回 | 操作同一 `student_admin_service`；学生端同步使用 pending 等当前枚举和 `apply_id` |
| 学生投诉 | 提交、本人详情、确认、重开、评价；路径由学生模块统一 | 操作同一 `service_ticket`；解决通知也由选定的 business 通知通道投递 |
| 学生通知 | 本人收件与已读入口 | 当前学生端也需适配工单来源 `business_notification`，不能只查询 student 通知表 |
| 学生心理 | 风险分析、生成预警和学生交互 | 企业仅调用共同处置 service，不重复创建评估/预警或默认开放聊天原文 |
| 学业考务/申请进度 | 学生端教务节点与 CRM 进度查询、同步、提醒 | 当前已存在镜像表；本期不因建表就增建企业 CRUD，确需老师查看时另加授权只读入口 |
| 客服 | 课程、活动、报名、公开 FAQ、访客会话 | 客服留资可调用共享客户创建 service，使用 `source_reference` 追溯，不直接把报名人当作员工或学生 |
| 报告 | 原文档拟定 `/api/v1/report/generate`、`/report/{report_id}`、`/report/list` | 正式生成/保存复用报告模块；日报/工单/心理统计按当前表字段与授权范围供数 |
| 公共能力 | 员工认证、NL2SQL、语音、对象存储、通知渠道 | 复用实际公共服务；尚无最终契约的能力不编造服务地址和配置 |

当前脚本未包含旧客户研判文档的 `customer_info/customer_judgement` 等表，因此不在本企业方案中把这些表当成已存在依赖。来源引用可保留，真实研判结果由该模块接口提供。

## 9. 后台任务与实现组织

后台定时扫描直接用固定查询，不走 NL2SQL。按实体、业务轮次/版本、接收人及提醒时间段生成稳定去重键；发送前复核状态、责任人及权限。事项结束或移交后，不继续发送旧责任人的提醒。

两张通知表分别按自己的状态机与租约字段处理：学生通知为 `pending/processing/sent/failed/cancelled`，业务通知为 `pending/sending/sent/failed/dead_letter`，不能共用一段假设字段完全相同的 SQL。统一收件箱只做授权结果适配。外部投递允许有限重试，不承诺跨系统严格只发送一次。

本地写操作在短事务内占用唯一操作键、更新主表、保存必要事件、日志和通知；幂等键同参数返回原结果，不同参数返回 409。并发审批或改分的版本冲突不得静默覆盖。失败回滚，必要失败记录另事务保存。

CRM/教务外部写入先记录 `pending_external`，固定适配器确认后更新本地；结果不明记 `unknown_external`，查询外部结果或人工核对，不盲目重发创建请求。外部与本地不具备单一数据库原子事务，不把本地回滚等同于外部撤销。

实现时建议按 `api → schemas → services → models/公共客户端` 分层。请假、工单和预警的共同业务服务只有一份状态机与事务规则；企业路由只提供员工授权入口。通知 worker、索引回调和同步适配器使用可信服务身份，不开放成匿名业务接口。

## 10. 实施顺序与验收建议

| 阶段 | 交付范围 | 验收重点 |
|---|---|---|
| 1 | 认证、员工/部门、客户跟进、文字日报、学生关系及操作回执 | 权限隔离、唯一键、并发、历史、归档与责任移交 |
| 2 | 成绩、请假、投诉、心理人工处置、通知及待办 | 学生/员工共享同一事实、状态合法、两表通知不双发、收件人隔离 |
| 3 | 知识管理与问答、语音、NL2SQL、自然语言预览和确认 | 只读约束、对象澄清、签名绑定、确认重试不重复执行、知识来源正确 |

建议验收场景：

1. 学生提交请假后，老师列表查到同一 `apply_id`；批准后学生查到同一状态与意见。
2. 被转派的旧老师、无效学生关系、越权部门和错误版本均不能完成审批。
3. 两名员工并发改同一成绩或工单，只有满足当前版本的动作成功，重复请求不重复生成业务记录。
4. 相同幂等键提交不同参数返回冲突；相同确认凭证更换请求键也不重复创建客户或执行审批。
5. 日报临时预览不落正式表；修订与作废可追溯；同日提交不突破唯一键。
6. 内部投诉备注不计首次对外回应、不出现在学生端或通用 NL2SQL；解决后等待学生确认。
7. 工单通知只通过选定通知表入队，统一收件箱正确区分来源；同 ID 不会标记另一张表或他人消息。
8. 心理预警读取、统计和跟进按专属范围授权；普通主管或老师不自动获得全部内容。
9. 知识修改后旧索引与旧版本退出问答；发布检查审核、索引与有效期。
10. NL2SQL 越权、多语句和写入均被拒绝；外部结果未知时展示待核实。

本轮仅做仓库文件与方案静态核对，未执行建表、API 调用或数据库联调；上述场景为后续验收要求，不是已通过的测试结果。

## 11. 请确认的方案选择

建议按以下默认选择确认；可直接指出需要调整的条目：

1. **范围**：按第 5 节覆盖企业业务及老师心理预警处置，第 6 节维护接口优先复用已有公共服务；分阶段交付，不一次实现所有智能能力。
2. **数据基线**：以当前 `all.sql` 为准，使用 `student_profile + student_admin_service + service_ticket`，同步更新学生端、报告端的旧模型契约。
3. **通知/历史分工**：请假与心理走 student 配套表，工单走 service_ticket_record 和 business 通知；企业写操作统一保留 operation 回执，不双投递同一逻辑消息。
4. **流程**：请假单级审批；投诉解决进入待学生确认；心理预警人工接手、跟进和关闭；不自动超时关单。
5. **接口风格**：保留旧 customer/daily-report/nl2sql/command 路径，统一版本、稳定幂等、来源区分的通知 ID，自然语言写入先预览再确认。
6. **角色权限**：按第 12 节分配六个固定角色；建议在职业务账号同时配置 `employee` 以取得本人日报能力；分派、心理处置、学生主数据维护按该节附加条件显式配置，不把管理员解释为超级业务账号。

落地前仍需补充的外部信息：认证与公共查询实际契约、CRM/教务写接口、通知实际渠道、SLA 时长、心理处置授权与兜底分派人、课程和业务状态字典。本文已经给出不依赖这些实值的接口设计，未填写虚构地址、人员或密钥。

确认后再展开正式字段级 API 文档/OpenAPI 与实现任务；本文件本身不代表批准执行数据库迁移或上线。

## 12. 六个固定角色可调用的接口

### 12.1 依据、默认范围与阅读方式

角色来源为[企业智能助手功能与数据库设计方案 4.1](../../scripts/sql/bk/企业智能助手/企业智能助手_功能与数据库设计方案.md#41-固定角色无独立权限配置表)。当前仓库实际文件在 `bk` 目录；本节只采用其固定角色职责，业务表及字段仍按当前 `all.sql`。

| 角色代码 | 4.1 定义的角色 | 4.1 定义的默认范围 |
|---|---|---|
| `employee` | 普通员工 | 本人日报 |
| `consultant` | 客户顾问 | 本人负责客户、相关跟进及本人日报 |
| `manager` | 部门主管 | 本部门客户与已提交日报；子部门按固定配置明确 |
| `teacher` | 班主任/老师 | 有效关系分派的请假、学生及工单 |
| `academic` | 教务人员 | 授权学生/课程成绩 |
| `admin` | 管理员 | 员工、部门、知识配置；业务权限需相应角色 |

4.1 定义了角色和数据范围，未逐项规定新增、作废、分派等方法权限。以下是据此细化的**待确认接口授权方案**：公共员工入口见 12.2，各角色的业务接口见 12.3～12.8，原职责未明确覆盖的接口见 12.9。接口编号对应第 5、6 节，所有路径均省略 `/api/v1/enterprise`。

规则：

1. 所有六类角色共用认证、通讯录、授权知识、本人通知、智能交互和受限回执入口；这些入口不额外授予任何业务对象权限。
2. 不设置隐式角色继承。建议在职账号配置 `employee` 作为基础角色，其他职责通过 `role_codes` 数组兼任，例如 `["employee","teacher"]`。`consultant` 的本人日报已由原职责直接授予；单独 `manager/teacher/academic/admin` 不自动获得本人日报写入，需兼任 `employee`。
3. 允许一次业务操作，必须有一个角色规则完整满足“方法/动作 + 数据范围 + 当前对象条件”。不能用一个角色的功能搭配另一个角色的范围。
4. 下表为功能入口许可，仍须检查对象存在、责任人、有效期、状态、版本、外部权威来源及字段白名单。未列入默认或明确条件授权的接口一律不开放。
5. 条件权限是后端固定配置，不新增第七个角色、不增加动态权限编辑器，不接受前端或 Dify 自报授权。

| CUS-09 | GET `/customer/{customer_id}/followups` | 本部门客户跟进历史 |
| CUS-10 | PATCH `/customer/{customer_id}/followups/{followup_id}` | 可管理本部门客户跟进安排；更正历史正文仍限定本人原记录，其他人记录通过追加说明处理 |
| DAY-03 | GET `/daily-report` | 本部门 `submitted` 正式日报；其他员工的 void 记录不默认开放 |
| DAY-04 | GET `/daily-report/{daily_report_id}` | 同上，按提交部门快照校验 |
| DAY-07 | POST `/daily-report/summary` | 汇总本部门已提交日报，限制时间窗，返回来源 |

主管只有对团队日报的查阅/汇总权，不默认代写、修改、作废下属日报。本人提交日报需兼任 `employee`，对应 DAY-01、DAY-02、DAY-05、DAY-06；本人查询也按 employee 的本人规则执行。

部门主管不自动取得学生、成绩、请假、工单、心理预警或管理配置权限。兼任老师时，老师的学生范围仍来自有效关系及分派，不能扩成整个部门的学生范围。

### 12.6 班主任/老师 `teacher`

除公共入口外，默认可调用：

| 接口编号 | 方法与路径 | 数据范围/限制 |
|---|---|---|
| STU-01 | GET `/students` | 有效班主任/服务关系或有效业务分派确需访问的学生；只返回职责所需字段 |
| STU-02 | GET `/students/{student_id}` | 同上，不默认返回课程成绩或心理信息 |
| LEA-01 | GET `/leave` | 当前分派本人、有效学生关系内的申请；已审批历史仅返回本人实际审批且仍可访问的记录 |
| LEA-02 | GET `/leave/{apply_id}` | 同上，不能按姓名扩大范围 |
| LEA-03 | POST `/leave/{apply_id}/decision` | 当前 `reviewer_id=本人`、有效审批关系、`pending` 且版本匹配 |
| LEA-05 | GET `/leave/{apply_id}/records` | 仅有权申请的必要审批时间线 |
| TIC-01 | GET `/tickets` | 当前分派本人且有有效服务关系的工单；回避被投诉事项 |
| TIC-02 | GET `/tickets/{ticket_id}` | 同上，不能读同部门其他老师的全部工单 |
| TIC-04 | POST `/tickets/{ticket_id}/follow` | 当前授权处理人工单，区分对外回应与内部备注 |
| TIC-05 | POST `/tickets/{ticket_id}/resolve` | 当前授权处理人、`processing`、版本匹配；仅进入待学生确认 |
| TIC-06 | GET `/tickets/{ticket_id}/records` | 仅授权工单时间线；内部备注再按必要知悉范围过滤 |
| ADM-11 | GET `/students/{student_id}/staff-bindings` | 只查该授权学生与本人有关的职责、有效期和课程范围，不读取他人的完整授权配置 |

本人日报写入需兼任 `employee`。仅有 teacher 角色不能录入/更正/作废成绩，需兼任 `academic`，并满足成绩人员关系与课程范围。

LEA-04 审批分派、TIC-03 工单分派及全部 MEN 接口不是所有老师默认拥有，按 12.9 的职责条件开放。被设为工单处理人或预警负责人也不能绕过有效身份、专属权限与利益冲突检查。

### 12.7 教务人员 `academic`

除公共入口外，可调用：

| 接口编号 | 方法与路径 | 数据范围/限制 |
|---|---|---|
| STU-01 | GET `/students` | 有效成绩管理关系内的学生，不能扩大到全校 |
| STU-02 | GET `/students/{student_id}` | 授权学生的必要基本档案 |
| SCO-01 | POST `/scores` | 授权学生 + `score_editor` 关系 + 课程范围；教务权威系统有可写能力时才开放 |
| SCO-02 | GET `/scores` | 授权学生及课程的成绩 |
| SCO-03 | GET `/scores/{score_id}` | 同上，按记录中的学生/课程校验 |
| SCO-04 | PATCH `/scores/{score_id}` | 授权范围内更正得分/满分，原因必填，不移动业务键 |
| SCO-05 | POST `/scores/{score_id}/void` | 授权范围内作废，原因和版本必填 |
| ADM-11 | GET `/students/{student_id}/staff-bindings` | 只查看本人与该学生相关的成绩授权及课程范围 |

本人日报需兼任 `employee`。教务人员不默认拥有请假审批、投诉处理、心理处置、学生档案维护或关系授权写权限。不能自行给自己追加 `score_editor` 关系扩大改分范围。

### 12.8 管理员 `admin`

除公共入口外，可调用员工、部门和知识配置接口：

| 接口编号 | 方法与路径 | 数据范围/限制 |
|---|---|---|
| ADM-01 | POST `/departments` | 平台授权维护的组织配置 |
| ADM-02 | PATCH `/departments/{department_id}` | 修改部门配置，检查层级和主管有效性 |
| ADM-03 | POST `/departments/{department_id}/status` | 部门启停，先处理依赖 |
| ADM-04 | POST `/employees` | 员工主档、受控登录映射及初始角色 |
| ADM-05 | PATCH `/employees/{employee_id}` | 员工资料配置，不等于访问该员工的业务日报 |
| ADM-06 | POST `/employees/{employee_id}/status` | 员工启停/离职，检查未移交责任；业务移交仍走相应业务角色 |
| ADM-07 | PUT `/employees/{employee_id}/roles` | 后端允许的六种角色分配，必须审计；不能提交自由权限表达式 |
| ADM-14 | POST `/knowledge` | 创建知识草稿 |
| ADM-15 | PATCH `/knowledge/{knowledge_id}` | 修改知识及访问范围，失效旧审核/索引 |
| ADM-16 | POST `/knowledge/{knowledge_id}/publish` | 有审核发布职责、当前版本及索引 ready 等条件满足后发布 |
| ADM-17 | POST `/knowledge/{knowledge_id}/disable` | 停用已发布知识并使旧检索结果失效 |
| ADM-18 | POST `/knowledge/{knowledge_id}/reindex` | 为当前内容版本提交索引处理 |
| ADM-19 | DELETE `/knowledge/{knowledge_id}` | 仅从未发布、无引用草稿，检查版本并保留回执 |

配套只读：ORG-02～ORG-04 可按员工/部门维护用途读取必要管理字段，仍不返回密文或密钥；KNO-01、KNO-02 可增加受控 `status` 筛选以查看草稿/停用知识；LOG-01、LOG-02 可查授权配置对象的变更及操作回执，不默认读取所有业务日志。

仅有 admin **不能**调用客户写接口、查看全公司日报、修改成绩、批准请假、处理学生投诉或读取心理预警。相应业务必须兼任对应业务角色并满足该角色范围；管理员修改角色的能力也不应在业务请求中被解释为自动拥有所有角色。

本人日报需兼任 `employee`。学生主档及关系维护 ADM-08～ADM-13 不属于 4.1 明确授予的默认范围，不能仅因路径在管理接口表中就全部赋给 admin，按 12.9 单独处理。

### 12.9 原角色表未明确授予的附条件接口

以下列出完整接口方案中需补充职责归属的能力；“条件”不由客户端传入，均在后端固定配置并留变更记录。

| 接口编号 | 方法与路径 | 建议角色及必要条件 | 未配置时 |
|---|---|---|---|
| LEA-04 | POST `/leave/{apply_id}/assign` | `teacher` 中被指定的请假分派负责人；限制到明确学生/组织路由范围、待审批状态，不能仅凭 admin 或 manager 放开 | 默认拒绝；待分派异常只向授权路由人员展示最小信息 |
| TIC-03 | POST `/tickets/{ticket_id}/assign` | `teacher` 中被指定的服务分派负责人；限定处理部门、可分派人员与回避规则 | 默认拒绝；一般处理老师仅跟进已分派工单 |
| MEN-01 | GET `/mental/warnings` | `teacher` + 心理专属处置功能 + 明确学生范围；通常限定当前 `follower_id=本人` | 默认拒绝，连计数和原因也不返回 |
| MEN-02 | GET `/mental/warnings/{warning_id}` | 同上，只读处置必需信息 | 默认拒绝 |
| MEN-03 | POST `/mental/warnings/{warning_id}/assign` | `teacher` 中被指定的心理分派负责人；单独配置路由范围；未具内容权限时仅见最小路由字段 | 默认拒绝 |
| MEN-04 | POST `/mental/warnings/{warning_id}/ack` | 专属授权 teacher、当前负责人、有效关系、pending 和版本匹配 | 默认拒绝 |
| MEN-05 | POST `/mental/warnings/{warning_id}/follow` | 专属授权 teacher、当前负责人、processing 和版本匹配 | 默认拒绝 |
| MEN-06 | POST `/mental/warnings/{warning_id}/close` | 专属授权 teacher、当前负责人、processing、完整处置结果和版本匹配 | 默认拒绝 |
| MEN-07 | GET `/mental/warnings/{warning_id}/records` | 专属授权 teacher 且对该预警仍有处置/查阅权限，字段按必要性过滤 | 默认拒绝 |
| ADM-08 | POST `/students` | 优先可信教务同步服务；若需人工维护，建议给指定 admin 增加明确学生主数据维护职责及范围，属于待确认扩展 | 六个角色的默认业务权限均不包含该写入 |
| ADM-09 | PATCH `/students/{student_id}` | 同上；只改主数据白名单，不凭此授予成绩/审批权限 | 默认拒绝人工修改 |
| ADM-10 | POST `/students/{student_id}/archive` | 同上；另检查未结束业务及归档原因 | 默认拒绝 |
| ADM-11 | GET `/students/{student_id}/staff-bindings` | teacher/academic 默认仅查自己的授权关系；完整配置列表仅供被指定的学生授权维护 admin | 无维护职责时拒绝查看完整关系列表 |
| ADM-12 | POST `/students/{student_id}/staff-bindings` | 被指定的学生授权维护 admin；固定允许的学生/员工/课程范围，防止自授关系 | 默认拒绝，不能凭 academic 或 teacher 自行授权 |
| ADM-13 | PATCH `/students/{student_id}/staff-bindings/{binding_id}` | 同上；结束旧关系、保留历史并处理待办责任，不扩张业务权限 | 默认拒绝 |

这些条件不新增权限表；通过固定角色配置与受控负责人/范围配置实现。真实人员和范围需业务方指定，不能凭当前 `student_staff_binding` 自动推导“谁可以修改授权关系”。若公共主数据服务已有这些职责，应直接复用，不重复开放企业人工维护接口。

### 12.10 多角色示例及权限验收

| 账号角色集合 | 可执行示例 | 仍不可执行的示例 |
|---|---|---|
| `[employee, consultant]` | 本人日报、本人客户及跟进 | 移交同事客户、查询关联学生成绩 |
| `[employee, manager]` | 本人日报、本部门客户管理、部门正式日报汇总 | 改写下属日报、审批部门内任意学生请假 |
| `[employee, teacher]` | 本人日报、有效分派的请假审批及工单处理 | 改成绩、无心理专属授权时看预警 |
| `[employee, academic]` | 本人日报、授权学生/课程成绩 | 全校改分、自行建立成绩授权关系 |
| `[employee, admin]` | 本人日报、员工/部门/知识配置 | 查看全员日报、代学生确认投诉解决 |
| `[manager, teacher]` | 主管按部门管理客户；老师按有效学生关系处理业务 | 用 manager 的部门范围扩大 teacher 的学生/工单范围 |
| `[admin, academic]` | 配置维护；按 academic 学生/课程范围处理成绩 | 仅因 admin 就对未授权学生改分 |

后续实现应验证：

1. 对第 5、6 节每个接口逐一做角色许可检查，未映射到规则的动作默认拒绝；不能只隐藏前端按钮。
2. 列表、详情、统计、通知跳转、历史和导出/汇总均使用相同对象范围，不能从旁路泄露。
3. 自然语言预览和确认调用同一业务鉴权；更改提示词、目标姓名、客户端角色或 department_id 不改变权限。
4. 角色取消、员工停用、关系失效、客户/申请/工单转派后立即按新范围校验，旧会话和旧确认凭证不保留写权限。
5. 管理员和部门主管无业务兼任时，不获得成绩、请假、投诉或心理的业务读写权。

本节仅补充方案中的角色授权清单；尚未实现鉴权配置，也未执行运行时权限测试。
