## 一、项目概述

### 1.1 项目目标

建设一套面向**潜在客户、企业员工和留学生**的智能业务系统，覆盖五大业务模块：

| 序号 | 模块 | 核心目标 |
|:---|:---|:---|
| 1 | 客户研判 | 接收文本、PDF、Excel 等客户资料，解析关键字段，按甲方《用户画像研判规则》判断是否符合两个产品要求，输出可复核结论 |
| 2 | 客服Agent | 覆盖公司信息、业务、留学政策、课程推荐、活动报名、FAQ 与闲聊，知识问答基于已审核资料，活动报名写入业务数据 |
| 3 | 企业智能助手 | 支持意向客户与日报管理、组织架构与新人指引、学生成绩/请假/投诉业务，以及安全的自然语言查询（NL2SQL）与指令处理 |
| 4 | 学生智能助手 | 支持请假、心理关怀与预警、售后工单、学业提醒、留学进度、海外生活问答与升学项目推荐 |
| 5 | 智能报告 | 生成客户经营分析、员工日报日/周报、学生心理健康周报与投诉处理周报 |

### 1.2 需求范围总览

五个模块各自覆盖的功能场景如下：

- **客户研判**：客户信息接入 → 格式识别 → 内容解析 → 关键字段提取 → 规则匹配 → 研判结果输出。
- **客服Agent**：公司信息咨询、公司业务查询、海外留学政策查询、课程与项目推荐、活动与讲座报名、常见问题自助解答、日常闲聊互动（共 7 大场景）。
- **企业智能助手**：意向客户录入/查询/状态更新、口述日报、管理日报查阅、组织架构查询、新人入职指引、学生业务综管。
- **学生智能助手**：行政服务、心理关怀、售后反馈、学业考务、进度追踪、生活支持、增值转化（共 7 大场景）。
- **智能报告**：全域客户经营分析报告、员工日报汇总报告（日/周）、学生心理健康周报、投诉处理周报。

## 二、系统架构设计

### 2.1 总体架构

系统由五大核心模块组成，共享底层能力层：

- **应用模块**：客户研判、客服Agent、企业智能助手、学生智能助手、智能报告。
- **共享能力层**：NLP 意图识别、RAG 检索增强生成、NL2SQL、语音识别、知识库管理、数据表 CRUD 接口、认证授权、文件解析、模型适配、向量检索、通知、审计。

### 2.2 技术架构分层

| 层级 | 说明 |
|:---|:---|
| 接入层 | 客服Agent、企业智能助手、学生智能助手、智能报告入口 |
| 应用层 | 客户研判、客服Agent、企业智能助手、学生智能助手、智能报告 |
| 能力层 | NLP 意图识别、RAG、NL2SQL、语音识别、Prompt 管理 |
| 数据层 | 业务数据表、知识库向量存储、FAQ 库、活动课程库 |
| 基础设施层 | 关系型数据库、向量数据库、文件存储、定时任务 |

建议采用**分层模块化服务**，先按模块边界实现清晰的服务接口；是否拆分微服务应在技术选型与部署规模明确后决定。

## 三、模块开发设计

### 3.1 客户研判模块

**模块职责**：接收多格式客户信息（文本、PDF 简历、Excel 表格），解析并结构化，基于《用户画像研判规则》研判，输出结论。

**核心流程**：客户信息接入 → 格式识别 → 内容解析 → 关键字段提取 → 规则匹配 → 研判结果输出。

**关键技术点**：
- 多格式文件解析：PDF 解析、Excel 解析、文本解析。
- 规则引擎：基于《用户画像研判规则》实现可配置、版本化规则匹配。
- 研判结果结构化输出，含命中/未命中规则、证据、置信/完整性提示与人工复核标志。

**依赖关系**：依赖《用户画像研判规则》文件；无前置模块依赖。

### 3.2 客服Agent模块

**模块职责**：公司信息咨询、公司业务查询、海外留学政策查询、课程与项目推荐、活动与讲座报名、常见问题自助解答、日常闲聊互动。

**核心流程**：用户输入 → 多意图识别 → 场景路由 → 知识库检索/RAG → 回答生成 → 活动报名闭环。

**关键技术点**：
- 知识库与数据源搭建：基础文件解析（《公司信息》《公司业务》《留学政策》）、FAQ 库、活动与课程数据库。
- AI 能力与提示词配置：多意图识别、年轻化闲聊人设、个性化推荐逻辑。
- 核心交互与业务闭环：RAG 精准问答（可追溯来源、避免幻觉）、活动报名闭环（幂等）。

**依赖关系**：依赖三份核心文档、历史高频咨询记录、活动与课程数据库。

### 3.3 企业智能助手模块

**模块职责**：意向客户录入/查询/状态更新、口述日报、管理日报查阅、组织架构查询、新人入职指引、学生业务综管。

**核心流程**：员工语音/文字输入 → NL2SQL/指令解析 → 数据表操作 → 结果反馈。

**关键技术点**：
- 核心数据表与 CRUD 接口设计（意向客户、员工日报、投诉反馈、学生成绩）。
- NL2SQL 开发（只读链路 + 安全校验）。
- 新人指南知识库（QA + RAG 两套方案）。
- 主动待办推送、指令式业务处理（映射白名单 API）。

**依赖关系**：依赖意向客户表、员工日报表、投诉反馈表、学生成绩表；依赖新人指南、公司规章制度、业务流程文档。

### 3.4 学生智能助手模块

**模块职责**：行政服务、心理关怀、售后反馈、学业考务、进度追踪、生活支持、增值转化。

**核心流程**：学生输入 → 多意图路由 → 业务处理 → 数据表写入/查询 → 结果反馈。

**关键技术点**：
- 核心数据表设计（学生行政服务、心理健康画像、心理预警、售后反馈工单）。
- 业务逻辑：多意图路由、审批闭环、系统对接（教务/CRM 适配器）、知识库搭建。
- AI 能力：风险识别、智能摘要、营销生成。

**依赖关系**：依赖四张数据表；依赖教务系统、CRM 系统；依赖海外生活指南、升学项目资料。

### 3.5 智能报告模块

**模块职责**：全域客户经营分析报告、员工日报汇总报告（日/周）、学生心理健康周报、投诉处理周报。

**核心流程**：数据采集 → AI 智能汇总与分析 → 报告生成 → 报告输出。

**关键技术点**：
- 客户特征聚类与智能归因。
- 日报核心进展、关键产出、潜在风险提取。
- 心理态势汇总与风险群体识别。
- 投诉智能分类、时效分析与预警。

**依赖关系**：依赖客户数据、员工日报数据、学生心理数据、投诉数据；依赖定时任务调度。

## 四、数据库设计

### 4.1 总体说明

数据库类型：**关系型数据库 + 向量数据库**。
- 关系型数据库：存储业务数据表。
- 向量数据库：存储知识库切片向量。

通用约定：主键自增 `BIGINT`，时间字段 `DATETIME`，字符集 UTF-8，JSON 字段用于结构化扩展数据，向量字段用于 RAG 检索。

| 模块 | 数据表 | 说明 |

| 客户研判 | customer_info | 客户信息（来源类型、原始内容、解析字段） |

| 客服Agent | knowledge_vector | 知识库向量（文档名、切片内容、向量） |

## 五、接口设计

### 5.1 通用说明

- **接口风格**：RESTful API
- **基础路径**：`/api/v1`
- **通用响应格式**：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

- **通用状态码**：

| 状态码 | 说明 |
|:---|:---|
| 0 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未授权 |
| 500 | 服务器内部错误 |

### 5.3 接口实现注意事项

- 当前接口文档为示例级契约，编码前需补齐认证方式、权限、分页、排序、筛选、字段约束、错误响应、幂等、限流与审计要求。
- 文件上传应采用 `multipart` 或受控对象存储引用，不宜将 PDF/Excel 原文直接塞入普通 JSON 字段；明确最大大小、格式白名单与解析失败反馈。
- 活动/课程字段需补充状态、有效期、名额、创建/更新人；报名表应关联客户/活动并设置防重复策略。
- 请假审批、投诉工单、心理预警需补齐处理人、状态变更时间、备注/处置记录、通知记录与幂等标识。
- NL2SQL 对外返回结果不应泄露数据库凭据或原始 SQL 细节，保留受控审计信息供管理员追查。

## 六、开发原则与关键边界

- **业务规则优先于模型判断**：客户研判应把甲方规则结构化、版本化；模型负责资料提取或解释，最终判定必须可追溯到具体规则。信息缺失时返回「待补充/需人工复核」，不得猜测。
- **知识问答可追溯**：RAG 回答关联来源文档、更新时间与片段；检索不到可靠依据时明确告知并转人工。留学政策等时效内容需有责任人和更新日期。
- **AI 不直接执行任意数据库操作**：NL2SQL 采用只读账号、表/字段白名单、SQL 解析校验、强制行数上限、超时与用户数据权限过滤；写操作只能映射到明确的业务命令/API，执行前确认对象和影响。
- **身份和权限贯穿全链路**：区分访客、学生、员工、班主任、管理员等角色，按本人/班级/部门范围授权。心理健康与投诉信息最小化访问、加密传输存储、记录审计。
- **高风险心理事件由人接管**：模型输出仅作风险提示，不作诊断。高危命中后走经业务方确认的通知与人工响应流程，保存必要证据与处置状态。
- **外部系统采用适配器**：教务、CRM、申请系统、消息渠道通过适配层接入，明确鉴权、字段映射、超时、重试、幂等与降级策略。

## 八、非功能需求

## 九、验收标准

### 9.1 客户研判

- 支持文本、PDF 简历、Excel 表格等多格式解析。

## 十、待确认事项与风险

1. **代码与技术栈**：仓库目前未提供应用源代码、依赖清单或部署说明，需先确认语言、框架、模型、关系数据库、向量库与运行环境。
2. **研判规则**：未发现《用户画像研判规则》原件及两个产品的名称/代码、条件与标注样本，这是客户研判开发与验收的前置条件。
3. **外部数据**：公司信息、业务、留学政策、FAQ 历史记录、新人指南、生活指南、升学项目资料及教务/CRM/申请系统接口资料均需业务方提供并指定更新责任人。
4. **模块范围差异**：开发设计将组织架构、新人指引、学生成绩等列入企业助手，接口文档覆盖不完整；学生需求含心理关怀、学业提醒、生活支持、升学推荐等，接口文档尚无完整对应接口。
5. **数据模型差异**：企业助手含投诉与成绩表，学生助手另有售后工单表，需决定统一模型还是服务接口共享；意向客户字段需拆分跟进记录表。
6. **接口差异**：研判接口示例返回单一产品结果，但需求要求判断两个产品；文件上传、审批回调、提醒、组织架构、语音、报告五种类别等接口需补全。
7. **NL2SQL 目标差异**：总结建议只读 SQL 与人审安全能力，接口示例返回 SQL；需明确是否向用户展示 SQL，生产环境禁止模型执行写 SQL。
8. **心理安全流程**：需明确风险等级定义、告警接收人、响应时限、非工作时间联系人、学生知情与隐私告知、数据保留与人工关闭规则。
9. **报告指标与数据缺口**：同环比周期、客户转化路径、成交价值、流失归因、心理群体指标、投诉满意度尚无统一口径，当前表结构不足以支持全部分析。
10. **账号与权限**：需提供员工/学生/班级/部门身份源、角色职责、数据可见范围、管理员与审计员定义及账号注销与权限回收流程。

## 十一、建议的首批开发顺序

1. 先定技术栈、接口规范、统一身份/权限与数据字典。
2. 先完成基础工程、业务数据表与审计，再做确定性 CRUD 闭环。
3. 以客户研判（规则可拿到时）与客服Agent 为首批 AI 场景，建立评测、知识更新与人工兜底流程。
4. 再做企业助手录入/查询/更新、学生请假与投诉闭环；NL2SQL 与自然语言写操作在权限与审计就绪后上线。
5. 心理预警在人工响应机制完成演练后开放；报告最后接入稳定数据并逐项核对指标。

> 共享数据模型、权限与外部接口契约应先冻结，避免多个模块各自定义同一业务对象。
