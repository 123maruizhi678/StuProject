## 一、角色、权限与接口的关系

受保护接口的授权关系为：

```text
账号密码 → 登录接口 → JWT
                       ↓
请求受保护接口 → 校验 JWT → 根据 sub 查询 user_account
                       ↓
取得真实 identity_type → 根据 access_control.yaml 计算权限集合
                       ↓
检查接口声明的 require_permission(权限标识)
                       ↓
业务层检查本人/部门/学生关系、员工角色、分派和业务状态 → 执行业务
```

| 层次 | 判断依据 | 与接口调用的关系 |
| --- | --- | --- |
| 身份认证 | 有效 JWT、真实账号记录 | 确定当前请求是谁；登录成功不代表可以调用所有业务接口 |
| 接口权限 | `identity_type` 对应的配置权限 + 接口声明的权限标识 | 只有具备接口所需权限，才能继续执行受保护业务 |
| 数据范围 | 业务关联 ID、员工角色、部门、学生关系、分派、状态 | 进一步限制允许操作哪些具体记录 |
| 公开访问 | 接口明确允许匿名 | 登录、公开访问清单和六个客服接口按公开规则调用 |

`user_account` 当前没有独立的 `permissions` 字段，公共鉴权也未查询独立的用户权限关系表。当前采用“账号身份 → 配置权限 → 接口鉴权”的方式，不能描述为已经支持逐账号独立授权。前端菜单可见性不代替后端接口鉴权。

## 二、角色与权限清单

| 角色 | identity_type | 配置权限 | 数据范围与限制 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `admin.dashboard` | 当前只有管理员看板权限，不自动继承员工、客户、学生的权限 |
| 员工 | `employee` | `dashboard.employee`、`student.profile.read`、`student.admin_service.review`、`service_ticket.read`、`service_ticket.handle`、`report.read` | 仍需检查员工角色、部门、学生关系和分派范围 |
| 客户 | `customer` | `dashboard.customer`、`course_project.read`、`event_signup.create`、`service_ticket.create`、`service_ticket.read_own` | 限本人业务范围，不能因此访问学生身份的数据 |
| 学生 | `student` | `dashboard.student`、`student.profile.read_own`、`student.admin_service.create`、`student.admin_service.read_own`、`student.notification.read_own` | 限本人学生业务；不能审批请假或查看其他学生数据 |
| 匿名访客 | 无有效登录身份 | 无登录权限集合 | 可以调用明确公开的接口，不需要 visitor Token |

顾问、主管、老师、教务等员工业务角色不能仅靠 `employee` 身份区分；业务层还需结合员工角色及关系校验。源文档提到 `employee.role_codes`，但未给出完整子角色授权表，本文不自行分配。

## 三、已明确的 HTTP 接口访问矩阵

“公开”表示无需 JWT 即可请求；登录接口仍须校验账号密码。“本人”表示须通过 JWT 认证且身份已配置，只查询当前账号。

| 方法及接口路径 | 匿名访客 | 管理员 | 员工 | 客户 | 学生 | JWT / 权限依赖 | 功能及边界 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `POST /api/v1/auth/login` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求已有 JWT；校验提交的账号密码 | 成功签发 `access_token`、`token_type`、`expires_in` |
| `GET /api/v1/auth/public-access` | 公开 | 公开 | 公开 | 公开 | 公开 | 无需 JWT | 返回公开页面/模块元数据，不代替业务接口授权 |
| `GET /api/v1/auth/me/access` | 不允许 | 本人 | 本人 | 本人 | 本人 | `get_current_account`；源文档未列额外权限标识 | 返回当前账号身份、权限、可访问页面和模块，不能指定其他账号 |
| `POST /api/v1/agent/chat` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 客服对话、会话及消息记录；仅此客服接口涉及 Dify 调用 |
| `GET /api/v1/agent/events` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 活动列表，支持按 `status` 筛选 |
| `GET /api/v1/agent/events/{event_id}` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 查询活动详情 |
| `POST /api/v1/agent/events/signup` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 校验活动、名额和有效报名记录，成功返回 `signup_id` |
| `GET /api/v1/agent/courses` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 返回上架课程，支持按 `category` 筛选 |
| `GET /api/v1/agent/faq` | 公开 | 公开 | 公开 | 公开 | 公开 | 不要求 JWT，不设置角色权限依赖 | 关键词模糊查询，未命中返回第一条 |

上述共 9 个明确路径：3 个公共接口、6 个客服接口。接口路径是源文档约定，不代表均已挂载可用；源文档记录客服路由挂载仍为注释，实际访问状态待核验。

## 五、接口调用链与公共组件关系

| 入口 | 调用关系 | 主要数据 / 结果 |
| --- | --- | --- |
| 登录 | auth 路由 → auth_service → 查询账号及校验密码哈希 → 签发 JWT | `user_account`；返回登录凭据 |
| 公开访问清单 | auth 路由 → `public_access` → YAML 配置 | 公开页面及模块信息 |
| 当前账号权限 | `get_current_account` → 查询账号 → `access_for` → YAML 配置 | 当前账号身份、权限及可见页面/模块 |
| 受保护业务接口 | `Depends(require_permission(...))` → JWT 认证 → 账号身份映射权限 → 业务范围校验 → 业务服务 | 接口权限与记录级访问控制共同生效 |
| 客服对话 | agent 路由 → `run_chat` → 会话/消息处理 → 客服场景客户端 → 返回回复及动作 | `chat_session`、`chat_message`；real 目标链路复用 `DifyHttpClient` 调用 Workflow |
| 客服活动列表 / 详情 | agent 路由 → `list_events` / `get_event` → 公共数据库会话 | `lecture_event` |
| 客服课程列表 | agent 路由 → `list_courses` → 公共数据库会话 | `course_project`，仅上架课程 |
| 客服报名 | agent 路由 → `signup` → 活动及有效报名校验 → 业务事务 | `lecture_event`、`event_signup`；写报名及更新人数 |
| 客服 FAQ | agent 路由 → `search_faq` → 公共数据库会话 | `faq` |

公共鉴权组件是后端依赖，不是需要前端额外请求的独立“鉴权 HTTP 接口”。日志、统一返回、数据库会话和 Dify HTTP 工具属于公共能力，也不直接赋予调用者业务权限。

前端收到客服 `show_courses` / `show_events` 动作后，再请求对应课程 / 活动列表接口展示真实业务数据；报名由前端提交到报名接口。浏览器不直连 Dify，Dify 不直接写业务数据库。

## 六、身份与调用凭据的边界

| 标识 / 凭据 | 作用 | 权限边界 |
| --- | --- | --- |
| 平台 `access_token`（JWT） | 浏览器调用需要认证的后端接口 | 验证签名及有效期，再查询真实账号；权限来自当前账号身份和服务端配置 |
| Dify 应用 API Key | 后端调用 Dify 应用 | 仅服务端使用，不是平台 JWT，也不授予用户接口权限 |
| `user_account.user_id` | 平台账号主键 | 不能当作 `employee_id`、`customer_id` 或 `student_id` 使用 |
| 账号关联业务 ID | 将账号关联至员工、客户或学生业务记录 | 对应身份只填写自身关联项，其他项为空；管理员三项均为空 |
| 客服 `session_id` | 关联多轮会话 | 不是账号身份或接口授权凭据 |
| 客服请求 / 会话 `user_id` | 可选字符串访客标识 | 不等同于平台账号主键，不能信任为已登录身份 |
| 报名手机号 | 联系与有效报名判重 | 不自动创建账号，不自动获得客户或学生权限 |

客户与学生档案之间存在业务关联，也不自动授予客户账号访问学生数据的权限。已登录角色调用客服接口时，不能额外获得会话历史查询、报名名单导出、课程维护或活动维护能力；源文档没有列出这些管理接口。

## 七、鉴权结果与待确认项

| 情况 | 处理口径 |
| --- | --- |
| 受保护接口缺少有效 JWT、JWT 无效或过期 | 按 401 未认证处理 |
| 已通过认证，但不具备接口声明的权限 | 按 403 禁止访问处理 |
| 已具备接口权限，但记录归属、分派或状态不符合要求 | 由业务服务继续校验并拒绝不允许的操作；具体错误按业务约定 |
| 请求公开客服接口 | 不因缺少 JWT 或角色权限而拒绝；仍执行参数和业务校验 |

401 / 403 是源文档的鉴权语义，不能保证所有路径均使用对应 HTTP 状态。源文档记录：部分异常采用 HTTP 200 搭配 `code/message/data` 业务码，部分路径仍可能返回框架格式或实际 HTTP 错误状态，异常出口尚待统一。

5. IP 限流、验证码、手机号校验、状态式报名判重属于访问防护和业务校验，不属于角色权限；不能据此认定相关能力已经部署。
