# 学生助手统一鉴权接入方案（待确认）

日期：2026-10-15。本文件只提出接入方案与取舍，未修改业务代码、数据表或线上鉴权行为。组长实际接口地址、字段和统一鉴权依赖尚未在当前本地代码中确认。

## 推荐结论

登录、JWT签发/校验、刷新与退出统一由组长负责；学生模块通过他的公共鉴权能力获取可信当前用户，再执行本模块的数据归属、审批关系与状态检查。学生模块停止自行签发登录凭证，不持有组长的JWT签名私钥或共享签发密钥。

“先经过他的登录接口拿到Token”仍不足以保护后续学生业务请求；每个受保护请求都必须经过组长的统一校验能力，取得可信身份。不能只解码JWT内容，也不能信任前端传入的学生ID、员工ID或已登录标记。

## 调用方式与优劣

| 接入方式 | 优点 | 代价/适用条件 | 建议 |
|---|---|---|---|
| 同一FastAPI应用复用组长的get_current_user/中间件 | 一个认证实现；无额外自调用HTTP请求；便于统一异常与测试 | 依赖公共认证模块及CurrentUser契约，需要约定稳定导入位置 | 同进程部署时优先 |
| 学生服务调用组长的身份校验接口 | 学生无需解析或校验JWT；跨服务边界明确；可统一处理失效与吊销 | 每次请求有额外网络开销；认证服务异常会影响受保护接口 | 独立服务或组长明确要求HTTP接口时采用 |
| 各模块复制JWT校验或共享签发密钥 | 独立验证时可减少远程请求 | 重复维护；密钥范围扩大；策略和吊销处理容易不一致 | 不作为本次方案 |

同进程模式仍由组长维护唯一鉴权实现，学生仅声明依赖；若组长明确指定HTTP接口，不另行改成本地校验。

## 身份认证与业务授权分工

| 事项 | 组长统一能力 | 学生模块 |
|---|---|---|
| 登录、签发/刷新/退出、JWT有效性、吊销 | 负责 | 调用统一能力，不再自行实现 |
| 用户类型、账号身份、角色/服务scope | 提供权威结果 | 校验返回契约并映射为内部Principal，不接受前端覆盖 |
| 统一用户ID与学生/员工主键对应 | 提供稳定subject或业务主键约定 | 按可信映射定位student_profile/employee；不能默认user_id=student_id |
| 学生只能查看本人申请/工单 | 返回可信身份 | 按记录student_id强制过滤 |
| 老师是否负责该学生、是否为当前审批/预警负责人 | 提供角色/权限 | 查有效绑定与记录负责人，执行本模块业务授权 |
| 学生归档/在读状态、员工业务有效状态 | 负责统一账号状态 | 保留本地业务状态检查；角色来源与组长约定，避免两套角色来源相互冲突 |
| 同步任务 | 提供服务身份及同步权限 | 校验student:sync等约定scope，不伪装为学生或老师 |
| 幂等键、状态流转、版本冲突、事务和通知 | 不承担学生业务规则 | 保留现有实现 |

## 两类业务凭证需要单独处理

当前sign_token/verify_token同时承担三种用途：登录身份student-api、确认办理student-action、会话绑定student-conversation。组长接管登录鉴权后，后两者仍需保留防篡改、归属绑定及过期检查，不能直接把登录JWT当作办理确认凭证。

首期将业务凭证与登录认证模块分离，明确它们仅用于“确认哪一次操作、继续哪一个会话”，每次调用仍须先通过组长统一鉴权。若要求学生模块完全不再使用JWT格式，则改用随机action_id/conversation_handle，状态存入服务端的公共Redis或技术记录表；确认时检查操作者、有效期和固定参数，并保留幂等回执。存储与并发处理会增加实施量，因此需随接口契约一起确定，不能以删除校验代替迁移。

## HTTP模式的调用规则

1. 读取请求Bearer Token，学生后端通过组长指定的可信服务地址验证，调用方认证和传参格式完全按他的接口约定；不把登录Token转发给Dify等无关外部服务。
2. 只有明确有效且字段完整的结果才生成Principal；统一用户与业务主键映射失败时不办理业务，不自动创建同名账号。
3. 无效/过期凭证返回统一未登录结果；身份有效但权限不足返回无权限结果；认证服务超时或故障返回依赖不可用，不降级成匿名或本地签发身份。
4. 首期不缓存认证结果，同一个请求内复用已取得的身份，避免重复验票。后续确需缓存时，与组长约定吊销/权限变更的可接受延迟，缓存不能超过Token有效期。
5. 认证异常在学生边界适配小组最终约定的HTTP及业务code，不默认假定组长也采用HTTP200信封。Token与密钥不进入日志。

## 统一接入的总体优劣

| 方面 | 好处 | 需要承担的代价 |
|---|---|---|
| 小组协作 | 一处登录、多模块共用身份，减少接口口径差异 | 需要组长先给稳定身份契约与可用测试账号 |
| 维护与密钥 | 学生侧不维护登录算法和签发密钥，登录策略统一更新 | 公共接口变动需要协调、适配与回归 |
| 有效性与撤销 | 统一服务可集中执行退出、禁用和吊销策略 | 实际是否支持即时失效取决于组长实现；缓存会引入延迟 |
| 性能与可用性 | 同进程复用成本低；分工清楚 | HTTP模式增加耗时与依赖，需合理超时及故障表现 |
| 安全责任 | 统一认证入口，业务资源权限继续由学生服务严格执行 | 不能因为Token有效就放开所有学生或老师数据 |

## 落地顺序及验收

先取得组长接口/公共依赖及返回样例 → 确认业务ID、角色与服务身份映射 → 接入统一身份依赖 → 拆分业务凭证 → 更新文档与测试 → 使用组长测试账号联调。

验收覆盖：有效学生/老师/服务身份；过期/吊销Token；老师与学生越权；身份映射缺失；认证服务超时/错误返回；确认动作参数篡改、跨用户确认、重复确认；会话跨用户复用。旧的学生自签登录JWT在切换后不再被接受，组长服务不可用时不得回退到旧鉴权。

## 需要组长提供的内容

- 明确同进程公共依赖还是独立HTTP校验接口；仅有登录接口地址不够。
- 真实入口、调用方认证方式，以及有效、无效、过期和故障响应样例；不要在方案或聊天中传真实私钥。
- 当前用户对象中的稳定用户标识、student_id/employee_id或映射方式、用户类型、角色及权限字段。
- 统一错误码、有效期/刷新/退出/吊销规则、服务任务凭证方式，以及可用于联调的学生/老师身份。
